# ADR-001 多 API Key 派发：架构决策记录

> 记录「单 Key → 配置驱动多 Key」的迁移决策。PRD v2 已通过，本文固化六项决策、
> 兼容边界、并发/热更新契约与回滚规则。后续编码以本文为准。

---

## 一、背景与目标

YG Gateway 2.0.0 是单 `api_key` 鉴权：`httpauth.VerifyBearer(r, key string)` 单值
比较，两处调用点（`internal/server/handler.go:197`、`internal/panel/panel.go:203`）
均经 `livecfg.Snapshot.APIKey`。目标升级为**配置驱动的多 Key 派发**：

- 一个 `config.json` 里的 `api_keys` 数组，每把 Key 带稳定 `id`、`models` 白名单、
  `realm` 版本归属。
- 鉴权匹配走「SHA256 摘要前缀索引 → 完整摘要常量时间比较」，R5 红线不破。
- 旧单 Key 配置零迁移、行为逐位兼容。

---

## 二、决策记录（D-200 ~ D-205）

### D-200 Key 存储位置

- **选择**：A —— 并入 `config.json` 的 `api_keys` 数组。
- **理由**：与单值 `api_key` 同处，single source of truth；面板配置页透出零成本；
  深合并逻辑（`mergeConfigMaps`，main.go:563）已保证面板保存不丢该字段。
- **被弃方案**：B 独立 `keys.json` —— 引入第二个配置源，保存/加载/一致性都要双份，
  无收益。

### D-201 Key 哈希与存储边界

- **选择**：A 修正 —— 配置存明文，运行时索引只存 SHA256 摘要 + 元数据。
- **理由**：一期要求用户在 config 手填 Key，明文在配置源无法避免；但运行时**不复制
  明文**、日志/错误/接口响应不出现明文，把暴露面收窄到「配置文件」这一处。
- **被弃方案**：运行时也存明文（hub/ARP 做法）—— 倒退，违背 R5 既有常量时间摘要设计。

### D-202 前缀定义

- **选择**：B 修正 —— 摘要 hex 前 12 字符做索引前缀。
- **理由**：取**摘要**前缀而非原始 Key 前缀，避免不同 Key 格式歧义，也不在索引里
  保留凭证原文前缀。
- **边界**：前缀只缩小候选集，**不是身份认证本身**，最终校验必须是完整摘要。

### D-203 匹配顺序与碰撞

- **选择**：B 修正 —— `map[prefix][]candidate`，前缀桶可含多个候选。
- **理由**：避免 N 把 Key 线性遍历；`map` 平均 O(1) 定位，桶内常量时间比较。
- **碰撞契约**：前缀碰撞**不得覆盖**已有 Key；桶内对完整摘要逐项
  `subtle.ConstantTimeCompare`。不承诺严格 O(1)，只承诺平均 O(1) 定位 + 桶内比较。

### D-204 空值语义

- **选择**：B 修正 —— 显式配置但无有效 Key → **fail fast**（启动失败 / 保存被拒）。
- **理由**：不静默降级为免鉴权，避免配置错误意外开放接口。
- **边界**：区分「`api_keys` 键缺失」（旧配置 → 兼容）与「键存在但 `null`/`[]`/全空」
  （显式新配置 → fail fast）。判定靠自定义反序列化保留「键存在」信息。

### D-205 models 三态语义

- **选择**：A 修正 —— 缺失=不限 / `[]`=全拒 / 非空=白名单。
- **理由**：明确区分「未配置约束」与「明确禁止」，对齐 ARP 三态。
- **实现**：`[]string` 无法区分键缺失与显式 `[]`，需自定义反序列化或存在标记。

## 三、凭证安全契约

1. **明文边界**：`api_keys[].key` 明文只存在于 `config.json`；文件按敏感凭证处理
   （与 config.json 同级 `0o600`）。
2. **运行时**：索引只存 `sha256(key)` 摘要 + 前缀 + `id`/`name`/约束，不复制明文。
3. **比较**：完整摘要 `subtle.ConstantTimeCompare`；前缀仅索引。R5 承诺**限定在摘要
   比较原语及其使用方式**，不宣称整个 HTTP 流程无任何时序差异。
4. **日志/错误**：不记录 Key 明文、Authorization 原文；错误响应不泄漏「哪把 Key
   存在/匹配失败」细节（防探测存活 Key）。

## 四、兼容策略

| 场景 | 行为 |
|---|---|
| 旧配置只有 `api_key`（无 `api_keys` 键） | 2.0.0 逐位一致（含空 key=不鉴权、缺头/坏方案路径） |
| `api_key` 非空 + `api_keys` 有有效条目 | 单值 + 多 Key 均放行 |
| `api_key` 空 + `api_keys` 有有效条目 | 启用多 Key 鉴权 |
| `api_keys` 显式 `[]` / null / 全空条目 | **fail fast**（启动失败 / 保存被拒），不开放 |
| env `WB2A_API_KEY` | 只覆盖单值 `api_key`，**不覆盖** `api_keys` 数组 |

- 一期**不新增**多 Key env（控制面单一，多 Key 只走 config 文件）。
- 兼容判断必须区分「旧配置（键缺失）」与「显式新配置（键存在但空）」。

## 五、约束执行与身份一致性

1. **一次匹配**：请求先完成 Key 身份识别（得 `key_id`/`key_name` + 该 Key 约束），
   后续 `realm`/`models` 校验、日志归因**全部用同一次匹配结果**。
   - 禁止「模型不匹配就换一把 Key 重试」。
   - 禁止「校验与归因之间重新匹配」，导致身份不一致。
2. **执行顺序**：提取 Bearer + model → 鉴权（识别 Key）→ realm/models 校验 → 选号 → 出站。
   约束校验在选号/出站之前，被拒请求零上游消耗。
3. **realm 判定**：复用 `ResolveModel(model)`（resolve_model.go:26）得到目标 realm；
   规则：配置空=不限 / cn=只 cn / global=只 global / 其他值=配置校验失败。
4. **models 判定**：白名单比对用 `ResolveModel` 的 bare 名，大小写敏感、不 trim；
   请求缺 model 且 Key 配了 models → 400（不能因缺 model 跳过白名单）。
5. **上下文**：请求上下文只存 `key_id`/`key_name`，不存 Key 明文。

### 身份传递不变量（设计约束，后续改动必须遵守）

- **`authKeyKey`（handler.go 的 context 键）是 realm/models 约束校验的唯一身份来源**。
- **`requestTrace`（logging.go）只负责请求日志归因**，只存 `keyID`/`keyName` 两个字段，
  **不持有完整 `*httpauth.Key`**（避免重复持有含摘要的对象）。
- **两者必须来自 `withAuth` 中同一次 `authenticate(r)` 的返回值**，禁止在约束校验或
  归因处重新调用 `authenticate`/`Match`。
- 后续若调整鉴权链路，必须保持「授权身份」与「日志归因」一致；任何新增身份来源
  都必须回到同一次匹配结果，禁止引入第二次匹配。

## 六、并发与热更新契约

1. **原子快照**：配置更新在**独立对象**中完成校验、摘要计算、前缀索引构建，
   全部成功后**一次 `atomic.Store` 切换**。旧快照切换前保持可用。
2. **禁止并发改已发布数据**：发布后的 `map`/候选桶只读，任何修改走「构建新对象 →
   切换」路径，绝不在原地改已发布结构。
3. **失败回滚**：新配置校验失败 → 拒绝应用 + 保留旧快照 + 不落盘；首次启动无有效
   快照 → **启动失败**（与 D-204 fail fast 一致，禁止失败后退回免鉴权）。
4. **验证**：`-race` 下并发请求 + 配置切换，断言不读到半新半旧快照。

## 七、测试门禁

| # | 类别 | 关键场景 |
|---|---|---|
| 1 | 旧版兼容 | 无 `api_keys`、空 `api_key`、env 覆盖不回归 |
| 2 | 多 Key 正确性 | 单/多 Key 混用、重复 Key、重复 id、前缀碰撞、无效配置 |
| 3 | 安全性 | 完整摘要比较、未知 Key 拒绝、日志不泄漏、无效配置不开放 |
| 4 | 白名单 | models 缺失/`[]`/指定、缺 model、异常 model、流式+非流式 |
| 5 | 版本约束 | cn/global/空 realm、无法判目标版本 |
| 6 | 并发热更新 | `-race` + 原子切换，无半新半旧 |
| 7 | 出站协议 | 请求头/body/协议字段与改动前逐项一致（真实链路，非单测 httpauth） |
| 8 | 性能 | `go test -bench` + `-benchmem`，记录环境/Key 数/碰撞桶大小/结果 |
| 9 | 配置保存回归 | 面板保存后 `api_keys` 原样保留（真实保存→重读→热应用链路） |

**第 8 项（零分配）定位为可测量性能目标**：先测量、记录基准与碰撞桶规模；若实现
需要临时分配，先评估是否真的影响目标性能，**不为字面「零分配」牺牲正确性或可维护性**。

**基准实测（2026-10-11，i7-14650HX，Go 1.27.2，Windows/amd64）**：

| 基准 | 耗时 | 分配 |
|---|---|---|
| Match 1 Key | 110.3 ns/op | 0 B/op, 0 allocs |
| Match 10 Keys | 116.4 ns/op | 0 B/op, 0 allocs |
| Match 100 Keys | 173.0 ns/op | 0 B/op, 0 allocs |
| BuildIndex (100 keys) | 30.3 µs/op | 22.7 KB, 312 allocs |

鉴权热路径（Match）**零分配**；前缀索引 + 桶内常量时间比较不随 Key 数线性退化
（1→100 只从 110ns 涨到 173ns）。BuildIndex 的分配只在配置变更时发生，不在请求热路径。

## 八、回滚方案

1. **二进制回退**：部署前保留旧版 `.v{版本}`（R15），冒烟失败回退二进制 + 恢复
   `state.json`。
2. **Git 回退**：`git checkout` 丢弃编码阶段变更。
3. **移除 `api_keys` 回到单 Key**：⚠️ **有条件，不是无条件安全**。
   - 若单值 `api_key` 非空 → 移除 `api_keys` 后回到单 Key 鉴权，安全。
   - 若单值 `api_key` 为空 → 移除 `api_keys` 后回到「不鉴权」旧语义，**会开放接口**。
   - **回滚步骤必须**：先确认旧单 Key 配置有效性（`api_key` 非空），再移除 `api_keys`；
     若 `api_key` 为空，必须同时补上非空 `api_key` 或显式关闭对外监听，否则禁止以
     「移除 api_keys」作为回滚手段。

---

## 九、结论

六项决策（D-200~D-205）+ 四补充约束（原子热更新含完整快照 / 失败不破坏服务 /
realm+models 同一次匹配 / 零分配作可测量目标）+ 回滚陷阱（空 api_key 时移除 api_keys
不开放）均已固化。编码实现以此为唯一依据，不重新开启需求讨论。
