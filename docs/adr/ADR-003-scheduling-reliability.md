# ADR-003 调度可靠性：断路器 half-open / 全局准入 / 选号去写锁 / 分位数观测

> 来源：深度优化轮后端调研「需 ADR 的架构改动」中收益最高的四项。
> 前序：ADR-001（多 Key）、ADR-002（面板 Key 管理）已交付。
> 本文记录四项决策 + 兼容边界 + 并发契约 + 回滚。

---

## 一、背景

深度优化轮已完成低风险项（热路径去重解析、降锁、环形缓冲、404 信封、前端体验），
实测收益明确。本次处理调研中剩余的四个**承重墙级**改动——它们触及选号/冷却熔断
（调度核心），必须先用 ADR 固化边界，否则后续维护者会困惑于「为什么这样写」。

四项共同点：**都是"提高极端场景下的可靠性/可观测性"，不改变正常路径语义**。

---

## 二、决策记录（D-400 ~ D-403）

### D-400 断路器 half-open（熔断到期限速试探）

**问题**：`recordBreakerFailureLocked` 熔断后完全靠 `breakerUntil` 到期恢复——
到期瞬间若排队请求多，会**一次性全量**打上去；若号其实还是坏的，立刻二次熔断，
且 `retryCount` 已 +1、下次退避翻倍（最长 6h）。这是标准断路器的缺失环节。

**决策**：引入 **half-open 状态**——熔断到期后进入试探窗口，该窗口内**限速放行**
（每 `breakerProbeGap` 至多 1 次），成功即全量恢复（清 retryCount），失败则重新熔断。

**实现要点**：
- 新增 entry 字段：`breakerProbeAt time.Time`（上次试探时刻，不持久化——运行态）
- `healthy` 判定：熔断**未**到期 → 不可选；已到期 → 可参与，但 half-open 限速由
  pick 侧统一判定（不在 healthy 里做，因为限速需要「选中权」这个全局视角）
- pick 候选过滤新增：若账号处于「熔断刚到期」窗口（`!breakerUntil.IsZero() &&
  now.After(breakerUntil)` 且 `retryCount > 0`），且距上次试探 < `breakerProbeGap`
  → 本轮跳过（把它让给别的号；若无别的号，走兜底路径）
- 试探成功：`NoteSuccess` 已清 `retryCount` + `breakerUntil` → 天然全量恢复
- 试探失败：`NoteError` → `recordBreakerFailureLocked` 重新熔断（fails 从 0 累计，
  阈值后 retryCount+1 → 退避加倍）——**这正是期望行为**（坏号退避更久）

**为什么不改 healthy 而是改 pick**：`healthy` 被探活（`/healthz` 的 ServableNow）、
`CountsDetailed`（面板统计）共用。若把 half-open 限速写进 healthy，会出现
「面板显示不可用但实际能选中」或反之的口径漂移。限速是**选号策略**，不是**健康状态**。

**默认值**：`breakerProbeGap = 30s`（可配）。0 = 关闭 half-open（退化为既有行为）。

**被弃方案**：
- B「到期后固定冷却一段时间再放行」——那只是延长熔断，没解决"到期瞬间洪峰"。
- C「到期后随机放行 K 个请求」——需要跨请求计数，复杂且难测；时间窗更简单可验证。

### D-401 全局准入控制在途上限（429 + Retry-After）

**问题**：现有 `maxInFlight` 是**每账号**上限（`inFlightLimit`），整个网关的在途请求数
**无上限**。上游慢时请求会无限堆积（每个都占着 goroutine + 连接等超时），
最终内存/连接耗尽。这是防雪崩的关键缺口。

**决策**：新增**全局在途上限** `gateway.max_in_flight`（默认 0 = 不限，保持既有行为）。
超限时立即返回 **429 + `Retry-After: 1`**（OpenAI 错误信封，code=`server_busy`），
**不排队**。

**为什么不排队**：排队会掩盖问题（客户端以为在正常等待），且排队队列本身要限长、
要有超时、要处理取消——复杂度陡增；而 429 让客户端按自己的策略退避，语义更清晰，
与上游 429 的处理口径也一致（客户端已具备该能力）。

**计数口径**：全局在途 = 所有账号 `inFlight` 之和 + 排队中的？——不需要「排队中的」
（不排队）。直接用 `Pool.TotalInFlight()`（O(池大小) 累加 atomic）或维护一个
全局 atomic 计数。选**全局 atomic 计数**（在 `Acquire`/`Release` 处同增同减）：
O(1)、无锁、与既有租约语义天然同步。

**默认值**：0 = 不限（**默认关闭**，避免改变既有部署行为）。建议生产按账号数 ×
per-account 上限的 ~1.5 倍设置。

### D-402 选号热路径去写锁

**问题**：`pick` 持**写锁**遍历全池（map 遍历 + 每 entry 两次 prune + 权重计算 +
top5 排序 + 抽签）。选号是每请求必经，写锁是全池唯一串行点；QPS 高时是吞吐瓶颈。

**决策**：**分阶段**，本次只做**低风险的一半**——把写锁内**不修改共享状态**的工作
移出去（只读快照 + 锁内最小更新）。

**具体做法（本次）**：
1. `pruneExpiredModelCooldowns` / `pruneExpiredModelCosts` 改为**惰性 + 阈值触发**：
   不再每次 pick 对全池每个 entry 都跑；只在 entry 自身 map 长度超阈值（如 > 8）时清。
   —— 这砍掉写锁内 O(全池 × map) 的主要开销。
2. `costTier` 在 `:113 / :130 / :154` 被算**三遍**（全候选）→ 第一遍就缓存到切片复用。

**不做（明确排除，需更大改动）**：
- 把整个 pick 改成 `RWMutex` 读锁 + 版本化候选快照——需要维护「池版本号 + 快照
  失效重建」，且 `lastUsed`/`usedSeq` 的写回需要原子化或第二把锁，**回归风险高**。
  留待后续单独立项（届时需新的 ADR）。

**理由**：本次先拿"确定的收益 + 极低风险"的部分；把高风险重构留给有专门验证预算
的时候。这是**克制的范围控制**，不是遗漏。

### D-403 分位数观测（自实现固定分桶直方图，零新依赖）

**问题**：现有可观测性只有**均值**（`AvgDurationMs`、`AvgTPS`）。网关的痛点恰在
**长尾**（少数慢请求拖垮体验），而均值对长尾不敏感——一个 60s 超时能被 1000 个
50ms 请求稀释到看不见。

**决策**：自实现**固定分桶直方图**（`internal/metrics` 新包），零新依赖。

**规格**：
- 桶边界（毫秒，指数+细化的混合，覆盖网关关心的 1ms~120s）：
  `10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000, 30000, 60000, 120000, +Inf`
- 维度：全局 + 按模型（模型数有界，账号数也有界；**先做全局 + 按模型**，
  按账号按需再加）
- 估算分位数：桶内**线性插值**（不是取桶上界——那会系统性高估）
- 内存：14 桶 × 维度数 × 8B，可忽略

**为什么不引 `hdrhistogram`**：项目哲学是「最少依赖」（当前仅 12 个模块），
而固定分桶对本场景（延迟量级跨 4 个数量级、精度要求到"能看出 P95 比 P50 慢多少"）
完全够用。**不为一个可自实现的观测组件引入新依赖。**

**暴露方式**：`/status` 增加 `latency` 段（全局 + 按模型的 p50/p90/p95/p99 +
样本数）；面板用量页图表区展示。

## 三、兼容策略

| 场景 | 行为 |
|---|---|
| `breakerProbeGap = 0` | half-open 关闭，与改动前**逐位一致** |
| `gateway.max_in_flight = 0`（默认） | 全局准入关闭，与改动前**逐位一致** |
| 分位数观测 | 纯新增只读字段，不改任何既有输出 |
| pick 惰性 prune | 清理**时机**变化，**结果**不变（过期项照样被跳过与删除） |

**总原则**：四项全部**默认不改变既有行为**，需显式配置才启用（分位数除外，它是
纯增量观测，无行为影响）。

## 四、并发契约

1. **half-open 试探标记**（`breakerProbeAt`）在 `pick` 写锁内读写——与
   `lastUsed`/`usedSeq` 同处，无新增竞态。
2. **全局在途计数**用 `atomic.Int64`：`Acquire` 成功即 `Add(1)`、`Release` 即
   `Add(-1)`。要求**严格配对**（既有 `Release` 已幂等、且 handler 用 defer 保证）。
   计数器只增不减即为泄漏——加 `-race` 下的配对测试。
3. **直方图**：每桶 `atomic.Int64`（累加无锁）；读取时逐个原子读（快照非严格一致，
   对观测足够——分位数不需要跨桶快照一致性）。
4. 禁止在持锁时做 IO（既有红线，本次不引入）。

## 五、测试门禁

| # | 类别 | 关键场景 |
|---|---|---|
| 1 | half-open 生效 | 熔断到期后窗口内只放行 1 次；跨窗口后可再次试探 |
| 2 | half-open 恢复 | 试探成功 → retryCount 清 0 → 全量恢复（不再限速） |
| 3 | half-open 退避 | 试探失败 → 重新熔断且退避**加倍** |
| 4 | half-open 关闭 | `breakerProbeGap=0` → 与旧行为一致（到期即全量） |
| 5 | 全局准入 | 超限返 429 + Retry-After；未超限正常放行 |
| 6 | 全局计数配对 | 请求完成/失败/panic 后计数归零（无泄漏）；`-race` |
| 7 | 惰性 prune 等价 | 过期项仍被跳过（healthy 口径不变）+ 确实被删除（不无限增长） |
| 8 | 直方图正确性 | 已知分布 → p50/p95/p99 在容差内；边界值归桶正确；+Inf 桶 |
| 9 | 直方图并发 | `-race` 下并发写 + 读快照 |

## 六、回滚方案

1. **配置回滚**：`breakerProbeGap=0` / `max_in_flight=0` 即回到旧行为（无需改二进制）。
2. **二进制回滚**：部署前备份 `.v{版本}`（R15）。
3. **代码回滚**：四次改动各自独立提交，可单独 `git revert`。
4. 分位数是纯观测，回滚仅影响面板展示。

---

## 七、结论

四项决策固化：half-open 限速试探（不改 healthy 口径）、全局准入用 429 不排队、
选号只做低风险的一半去锁（大重构留后续 ADR）、分位数自实现不引依赖。
全部**默认关闭/纯增量**，回滚成本低。
