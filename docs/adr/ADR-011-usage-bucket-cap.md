# ADR-011 — usage 桶数容量保护：压力期收紧小时窗口 + 日桶丢弃安全阀

- 状态：已采纳（2026-10-20）
- 相关：`docs/prd/REQ-usage-bucket-cap-2026-10-20.md`；`internal/usage/usage.go`
- 影响面：`usage.Rollup`、`usage.usage.go` 的落盘大小与常驻内存

## 一、背景：上限形同虚设

`maxBuckets = 400_000` 是 v1 起就写死的桶数硬上限，但 `Rollup` 只折叠 **>90 天** 的小时桶（日桶永久保留）。稳态小时桶量 = 活跃组合（realm×uid×model×rate×key）× 90天×24小时，繁忙网关易超 40 万。触发上限后 `Rollup` 折不掉窗口内桶，桶数压不回上限 → 每新一小时又加新桶 → 相对上限**无界增长**。这是 `docs/code-review/2026-10-20-four-dimensions.md` 标出的 [P1]。

## 二、决策

1. **正常（桶数 ≤ maxBuckets）**：行为不变，只折 >90d 小时桶。
2. **超上限（桶数 > maxBuckets）**：小时保留窗口从 `hourlyKeep`（90d）**逐次减半**（90d→45d→…→`minHourlyKeep`=24h 触底），每轮把窗口内小时桶折成日桶，直到桶数压到 `target = 0.85×maxBuckets` 或窗口触底；触底仍超则把最老日桶聚合进合成「远古」日桶 `d:0001-01-01`（维度全空），直到桶数 ≤ target。
3. **`Snapshot`**：远古桶（维度全空）**只进 totals**，不进 `by_realm/by_account/by_model/by_key` 与逐日时序——避免 Years-ago 的聚合堆到图表最左端或生成空维度行。
4. **参数**：`maxBuckets=400_000`、`minHourlyKeep=24h`、`target=0.85×maxBuckets`，均为包内常量，注释引用本 ADR。

## 三、权衡与代价（明说）

- 压力路径下，「全部历史」卡片与按域/账号/模型的聚合在窗口收窄后会看到更粗的粒度（日而非小时）——这是**有意取舍**：用「部分历史从小时级降为日级」换「内存有界」。正常负载（桶数 ≤ 上限）完全不受影响。
- 日桶丢弃安全阀只在「折叠到 24h 触底后仍超上限」这种极端情形触发（多年级运行、日桶 = 组合×天数才会缓慢突破）。它把最老日桶合并进一个远古桶，**总量不丢**，只丢极老历史的按维度下钻与逐日时序点。正常负载永不触发。
- 不引入新配置项（保持单二进制零依赖、配置面不膨胀）；上限与窗口是包内常量，便于 `usage_cap_test.go` 用极小参数直接验证算法。

## 四、验收

| 用例 | 期望 |
|---|---|
| 桶数 ≤ 上限 | 仅折 >90d 小时桶，窗口内小时桶保留（行为不变） |
| 桶数 > 上限（全为窗口内小时桶） | 桶数降至 ≤ target，幂等（再调桶数/总量不变） |
| 触底仍超时日桶丢弃 | 桶数 ≤ target，总量不变，远古桶恰好 1 个 |
| 注入远古桶后 Snapshot | totals 含远古量，by_* / 时序不含 |

见 `internal/usage/usage_cap_test.go`。

## 五、回滚

改动单文件（`internal/usage/usage.go`）且纯内部、无 wire 变化，`git revert` 即可回到「上限形同虚设」的旧行为（旧行为不崩，只是无界增长）；不影响 `usage.json` 既有格式（远古桶是普通日桶，旧程序读它只当一条极老日桶）。
