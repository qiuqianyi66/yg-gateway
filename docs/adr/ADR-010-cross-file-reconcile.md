# ADR-010 — auths 目录与 state.json 的对账边界（B2 实质③）

- 状态：已采纳（2026-10-18）
- 相关：`docs/PLAN-open-items-2026-10-17.md` 的 B2 实质③；
  `.harness/wiki/cc-switch-deep-read.md` §6 的「该改」③
- 影响面：`internal/auth.LoadDir`（跳过留痕）、`internal/pool.SyncToDir`（空集下限）

## 一、背景：wiki 说的「无对账」在本仓**部分不成立**

wiki ③ 的原话是「跨文件操作的写前意图 + 启动前滚（`auths/*.json` 与 `state.json` 无对账）」。
现场勘察结论：

- **对账已经存在**：`cmd/server/main.go:132` 启动期调 `p.SyncToDir(auths)`，
  新账号加入、`auths/` 里消失的账号从池中剔除，且**立刻写回 `state.json`**
  （`pool.go` 的 `SyncToDir` 内 `saveLocked()`），注释明写「避免已删账号在下次启动时被 load() 复活」。
- 因此 ③ 里「完全没有对账」这个前提不成立；**不需要**再造一套对账。

## 二、真正缺的两件事（本次修复）

### 2.1 破坏性对齐缺少下限

`SyncToDir` 是**破坏性**操作（删状态 + 落盘，不可逆）。它的输入来自 `auth.LoadDir`，
而 `LoadDir` 对读不出/解析失败的文件是 `continue` —— 返回**短列表 + nil error**。
于是下列情形都会被读成「所有账号都被删了」：

- `auths/` 目录挂错 / 容器没挂卷；
- 权限变化导致全部 `ReadFile` 失败；
- 文件被批量改名（glob `workbuddy*.json` 不再命中）；
- 批量损坏。

后果：启动即把**全部**健康度观测（冷却、熔断、成功率、EWMA、成本台账）删掉并落盘。

**决策**：`len(auths) == 0 && len(p.byUID) > 0` 时**拒绝剔除**，打 WARN 说明可能是目录/权限问题。
需要真清空时走面板逐个删除（`Remove`，单账号粒度）或停服后手工处理 `state.json`。

### 2.2 跳过必须留痕

`LoadDir` 的 `continue` 历史上**完全静默**（`grep` 该函数内只有重复 UID 的 WARN）。
一个静默跳过的文件，在调用方眼里与「这个账号被删了」**不可区分**。

**决策**：两处跳过各打一条 WARN，点名文件路径与原因。保留「不因一个坏文件挡住启动」的历史行为
（这是合理的可用性取舍），但让人事后能查。

## 三、明确**不做**的事：写前意图日志

wiki 建议的「写前意图 + 启动前滚」在本仓**没有可保护的事务**：

- `state.json` 是单文件写（临时文件 + rename，已在 `saveLocked` 里）；
- `auths/*.json` 每个账号一个文件，各自独立写；
- `SyncToDir` 的「删 + 落盘」在同一把锁内完成，中间没有可崩溃的窗口。

凭空加一套 intent 文件只会新增一处需要维护的状态机和一种新的不一致来源。
**触发条件**（将来出现时再立 ADR）：出现**真正**跨文件、跨进程、必须全有或全无的操作，
例如「换版同时重写 auths 与 state」或「账号迁移（跨 realm 改 UID 且要带走状态）」。

## 四、验收

| 用例 | 期望 |
|---|---|
| 空扫描 + 池内非空 | 拒绝剔除，池内账号保持；WARN 一条 |
| 非空扫描 | 照常对齐（消失的删、新的加） |
| 目录里两个坏文件 | `LoadDir` 返回 0 账号、无 error，但 **2 条 WARN 且点名文件** |

见 `.harness/changes/2026-10-18-cross-file-reconcile/summary.md`。

## 五、代价（明说）

清空全部账号**不能再靠**「删掉 auths 目录里的所有文件后重启」——那种做法现在会被拒。
这是故意的：那种操作与「目录读不到」在系统看来完全一样，而代价差一个数量级
（后者是可修复的故障，前者只该走显式路径）。
