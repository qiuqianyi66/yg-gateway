# ADR-009 — 持久化文件的版本闸门（先做 usage.json）

- 状态：已采纳（2026-10-18，用户批准 B2 立项）
- 相关：`docs/PLAN-open-items-2026-10-17.md` 的 **B2 实质**；
  `.harness/wiki/cc-switch-deep-read.md` §6 的「该改」②
- 影响面：`internal/usage`（`New`/`load`/`LoadErr`）、`cmd/server`（启动期致命化）

## 一、背景：我们处在「旧程序读新文件」是常态的部署形态

本仓是 7×24 常驻 + 手工/脚本滚动换版，且**回滚是设计内的常规动作**
（`scripts/deploy-prod.ps1` 健康检查失败会自动回滚到上一版二进制）。于是：

- 新版程序把 `usage.json` 写成 `fileVersion=6`；
- 回滚后旧程序（支持 ≤5）启动，`load()` 只按 JSON 结构解析 —— 不认识的字段**按零值读入**，
  下一次落盘（5 分钟防抖）就把新字段**覆盖成零**。
- 结果：**静默、不可逆的数据损坏**，而且发生在「为了救服务才回滚」的时刻。

历史实现更糟：`New()` 对加载失败只打一行日志就「从零开始」——文件损坏、不可读、
版本不兼容全部走同一条路，台账整个丢掉，服务照跑，选号照选。

## 二、决策

给 `usage.json` 加**版本闸门**，并用 `LoadErr()` 把加载期错误暴露给启动方：

| 情形 | 行为 | 理由 |
|---|---|---|
| 文件版本 > 程序支持版本 | **硬错误 → 拒绝启动**（`cmd/server` 用 `log.Fatalf`） | 旧程序读新文件必丢字段；宁可让人看见，也不要无声污染 |
| 文件版本 < 程序支持版本 | 正常加载，并留 `<path>.pre-upgrade-v<N>.bak` | 迁移前备份（当前无字段变换，备份是廉价保险） |
| 版本缺失（0，老文件）/ 等于当前 | 正常加载，不备份 | 零迁移成本，旧数据必须能直接起来 |
| 文件损坏 / 不可读 | **硬错误 → 拒绝启动** | 与「从零开始」相比，丢失全部台账是更贵的失败 |

**为什么不用「自动迁移」**：目前没有任何字段变换需求（旧版本缺失字段按零值加载是**正确**语义，
不是错误）。加空的迁移框架只会增加维护面。等真有变换时再按同一闸门加 `migrate(v)` 即可。

## 三、代价与明说的风险

1. **回滚会遇到启动失败**：若新版写过 `usage.json` 而后回滚，旧版会拒绝启动 →
   `deploy-prod.ps1` 的健康检查失败 → 自动再回滚 → `exit 4`（生产可能不可用，需人工）。
   这是**故意的**：相比「起来了但台账被清零、选号依据被污染」，停机更可发现、更可恢复。
   操作路径写在错误信息里（换新版程序 / 用升级前备份替换）。
2. **`state.json` 未覆盖**（本轮范围外）。它连版本字段都没有，而且 `pool.load()` 对
   `json.Unmarshal` 失败**直接 return**（静默丢账号状态）——同族问题，但改成可失败会牵动
   `New()` 的构造签名（调用面很宽），需要单独立项。

## 四、验收（已实测）

`internal/usage/version_gate_test.go` 五个子用例：新版本→错误（且错误点名版本号）、
旧版本→可加载且留下备份、等于当前→不备份、缺版本→可加载、损坏→错误。
见 `.harness/changes/2026-10-18-ledger-version-gate/summary.md`。

## 五、替代方案与为何否决

| 方案 | 否决理由 |
|---|---|
| 静默从零开始（现状） | 数据不可逆丢失，且失败不可见 |
| 只打警告继续跑 | 同现状的变体：运维看不到，数据照样被覆盖 |
| 自动迁移（空框架） | 没有变换需求，纯增维护面 |
| 用 `state.json` 一把改完 | 牵动 `pool.New()` 签名与所有调用点，风险远大于收益；先做收益/风险比最高的一半 |
