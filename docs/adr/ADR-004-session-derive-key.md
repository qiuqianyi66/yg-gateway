# ADR-004 会话粘性：内容派生键改为可关闭（默认保持开启）

> 触发：实测发现「固定 system 提示词 + 短开场」的客户端流量会被内容派生键
> 判为同一会话，全量钉到同一个账号（`/status` 显示 4 个号健康、有积分，但
> 实际只用一个）。本文记录机制、复现证据与修复决策。

---

## 一、问题（实测复现）

**机制**：`session.ExtractKey` 在客户端没有显式会话标识时，按
`SHA-256(system 文本 + 首条 user 文本)` **派生**会话键（`deriveKey`）。
派生键相同 → 视为同一会话 → 会话粘性把它绑定到同一个账号。

**前提失效的场景**：很多客户端发**固定 system 提示词**，首条 user 又是短开场
（`hi` / `你好` / `继续`）。于是**互不相关的对话算出同一个键**。

**复现（修复前，同一实例）**：

| 实验 | 请求特征 | 结果 |
|---|---|---|
| A | 6 笔，**不同** `conversation_id` | 分散到 3 个号（账号A 2 / 账号B 2 / 账号C 2） |
| B | 4 笔，**相同** system + 相同开头、**不传**会话键 | **4/4 全落「账号A」一个号** |

B 就是用户观察到的「只有用一个号」。修复后再跑 B：分散到 3 个号，
`/status` 的 `sticky_sessions` 保持 0。

**加重因素（观察到的第二个现象）**：成本分层（`tier 0 免费 > tier 1 未知 > tier 2 实测收费`）
只在**还有未实测账号**时有效。一旦某个模型在所有号上都被实测出收费
（本例 glm-5.2：账号A 0.187 / 账号B 0.269），`bestTier` 变成 2，分层过滤退化为
**纯加权随机**——此时粘性进一步把流量固定在最先绑定的那个号上。

**第三个因素**：粘性路径 `Pool.PickByUIDForModel` 只校验
`healthyForModel` + 积分保底 + 在途，**不校验成本分层**。所以绑定号被实测为
收费后仍会持续被选中，而「优先免费/未知」的逻辑在粘性上是失效的。

---

## 二、决策

### D-500 内容派生键改为可关闭，默认**保持开启**

新增 `session_sticky.derive`（`*bool` 三态）：

| 取值 | 行为 |
|---|---|
| 键缺失（nil） | **开启派生**（与改动前逐位一致，零回归） |
| 显式 `true` | 开启派生 |
| 显式 `false` | **关闭派生**：只有客户端显式给标识才粘性 |

关闭后，无会话标识的请求回落**纯加权轮换**。

**为什么默认保持开启（而不是直接改默认）**：派生键的初衷是让「没有会话标识的
多轮对话」也能复用上游 prompt 缓存（省钱 + 更快）。它对**真正的多轮对话**是
有效的（system + 首条 user 在一次对话内恒定）。擅自改默认会让所有部署失去这一
收益，且属于静默行为变更。故以配置项形式提供，按部署取舍。

**为什么是开关而不是「更聪明的派生」**：能不能从请求里可靠区分「同一对话的
后续轮」与「另一段开头相似的对话」？在多轮协议里，第一轮请求无法与「另一段
首轮」区分——信息不足。任何启发式（如"首条 user 太短就不派生"）都是猜，
而猜错的代价（流量钉死一个号）比不粘性（少些缓存命中）更大。

### D-501 关闭派生是本实例的推荐配置

对**固定 system + 短开场**的客户端（多数 chat 客户端），建议
`session_sticky.derive = false`：显式会话标识仍保留粘性（那是客户端的明确
声明，可信且真正对应一次对话），无标识的请求打散到全池。

### D-502 修正 `session_sticky` 的重启项声明（R11）

`session_sticky.enabled` 与 `session_sticky.derive` 都是**装配期字段**
（前者决定 `session.New` 是否创建 router；后者在 `NewHandler` 时被复制进
handler 的 cfg，而 `saveConfig` 不重建 handler），运行期改不生效。
此前清单里只有 `ttl` / `gc_interval` → 面板保存后提示"已立即生效"却不生效
（用户以为开着粘性，其实没开）。现补全四个字段。

## 三、兼容与回滚

| 项 | 说明 |
|---|---|
| 既有部署 | 不改配置 → 行为逐位一致（`*bool` 零值安全：`nil` = 开启） |
| 回滚 | `session_sticky.derive` 设回 `true`（或删除该键）即恢复 |
| 显式会话键 | 两种模式下都命中，派生开关**不影响** `conversation_id` / `conversationId` / `prompt_cache_key` 的识别 |
| user_id 抑制 | 既有 anti-monopoly 契约（带 `user_id` 不派生）保留不变，优先级高于本开关 |

| 测试 | 断言 |

| `TestExtractKeyOptDeriveSwitch` | 开/关两模式下：派生键有无 + **显式键都命中且取值相同** |

| `TestExtractKeyOptShortOpeningCollision` | **固化问题本身**：相同 system + 相同开头的两段无关对话派生同一键 |
| `TestSessionStickyDeriveTriState` | `*bool` 三态解析（nil→开 / true→开 / false→关） |
| `TestSessionStickyEnabledIsRestartRequired` | 四个 `session_sticky.*` 字段都在重启项清单 |

## 五、被弃方案

| 方案 | 弃因 |
|---|---|
| B 直接改默认（关掉派生） | 静默行为变更，损害所有既有部署的缓存收益；且对真多轮对话是有用的 |
| C 「首条 user 太短就不派生」 | 启发式猜错代价大；且长开场同样可能重复（如固定模板 prompt） |
| D 粘性路径也走成本分层（绑定号变贵就换） | 与粘性的目的（缓存复用）直接冲突；换号会丢缓存，且"换号"本身要重建会话语义。分层该在**选号时**生效，不该在**已绑定**后推翻绑定 |
| E 禁用整个粘性（`session_sticky.enabled=false`） | 一刀切：连显式会话标识的正当粘性也丢了。故保留为粗粒度后备（已列入重启项） |

---

## 六、结论

派生键是「在信息不足时的猜测」，对真多轮对话有效、对开头相似的无关对话有害。
决策：**保留能力、提供开关、默认不变、本实例关闭**。
同时补全 `session_sticky` 的重启项声明，消除"提示已生效但实际未生效"的误导。
