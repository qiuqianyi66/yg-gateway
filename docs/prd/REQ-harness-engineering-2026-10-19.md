## 一、必要性（阶段 0，四个问题）

**Q1 要解决的真实问题是什么？**（实测，非"清单上写着"）

v0 时的三个问题（2026-10-19 实测）：

1. **治理层没有自检能力**：三个既有检查（依赖方向 / 体量棘轮 / 必要性段）都不回答
   "这套治理本身还自不自洽"，引用断链与数字漂移全靠人记。
2. **常驻上下文无预算门禁**：常驻层 22,603 token，tea 同口径 19,048 且自带 19,500 预算线。
3. **最大的常驻文件是经验池**：`LESSONS.md` 7,547 token，是 `AGENTS.md`（2,607）的 2.9 倍，
   而 `AGENTS.md` 要求"动手前先读 LESSONS"——事实常驻，却按按需资源膨胀。

**Q2 不做会怎样？** 静默漂移，不报错。本仓已为同类问题赔过两次（doc-drift、cross-file-reconcile）。

**Q3 现状是不是已经变了？** **变了两次，这是本文件必须更新的原因**：

- v0 时：yg 已有 tea 没有的硬机制（依赖方向机器校验 / 体量棘轮 / 部署排练 53 断言 / 四态语义），
  所以定位是"补自检 + 补度量"，不是"从零建 harness"。
- v1 时（2026-10-20）：**P0 已全部落地**——F1 一致性体检（4 检项实做 + 3 未测）、
  F2 上下文预算 + 棘轮、F3 经验池外置（常驻层 22,603 → 15,822）、F5 度量账本（2/5 组）。
  **所以现在真正未做的只剩 §八 那几项。**

**Q4 有没有更便宜的等效手段？** 有且已采用：只加只读脚本，不新增规则、不新增技能、不动 `internal/`。
P0 的实际代价是 3 个新脚本 + 1 个基线 json + 1 份技能路由表 + 1 份度量账本，**零新增规则、零新增技能**。

**结论：降级做（已执行）。** P0 = F1 + F2 + F3 + F5。**明确不做**"照搬 tea 全套 39 技能 / 13 CI job"，
这条至今有效，是本需求的反膨胀锚点。

## 四、范围边界

**已做（P0，2026-10-19 ~ 10-20）**

- F1 治理一致性体检（只读脚本，退出码即结论）
- F2 常驻上下文预算 + 棘轮（只许收紧）
- F3 经验池外置与索引化
- F5 度量基线账本（`docs/agent-eval/baseline-2026-10-19.md`）

**仍不做（明写，免得下轮重提）**

- 不新增任何技能；不做 harness 自动评测集（tea 七维评测）
- 不做子代理 / 多 agent 编排；不把网关本体改造成 agent（方向 B 需另立 REQ）
- 不做 wiki 契约漂移审计、红线机械化审计——**不是"永远不做"，是按 §六 Q4 两周判据决定**
- 不改 `internal/` 业务代码（2026-10-20 续作改的 `internal/panel` 测试取数方式是解假红，属例外，见 summary §5.1）

**边界外的风险**：F1/F2 把"治理数字"变成机器可校验对象，改技能数/规则数必须同步路由表与基线，
否则门禁红。这是**故意**的（把漂移变成红灯），代价是每次治理改动多一步同步。

### Q4 的两周判据（先写死，免得到时候改口径）

统计 F1 + F2 报出多少**真问题**（真问题 = 报出后确实改了东西；误报 = 报出后得改脚本才消掉，两者分开记）：

- **真问题 ≥ 1 且误报 ≤ 1** → 保留，并按命中类型决定是否补检项。
  2026-10-20 已按此补 [4][6][8] 三项（[4][6] 判据直接授权；[8] 针对已实证的盲区）。
- **误报 ≥ 3** → 先修判据，**不许**靠"习惯了这个红"继续用（那等于门禁失效）。
- **零命中** → **停手**，后续投入停止，不加漂移审计 / 红线审计 / 评测集。

当前读数（3 组口径）：真问题 **10**、误报 3（3 处误报全在 F1 开发期，已改判据，稳态后 0）。
其中 2026-10-20 新增 2 处（检项 [6] 咬出的两个 changes 目录缺 summary.md）——**这是机器报的**；
另有 1 处（pre-commit 检查 9 自己的描述漂移）是通读发现的，**不是机器报的**，两类分开记。
**开发期误报不计入稳态**；判据按"上线后稳态运行两周"计，不是按开发过程计。

**反向纪律**：不许为了让数字好看而改判据或改基线。基线只许下调（F2 脚本强制），
真问题数不许把误报算进去。
