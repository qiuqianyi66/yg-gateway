## 一、可复用结论（按主题）

### 1. 架构与分层

- 依赖只向内：`domain/contracts ← provider ← application ← CLI/HTTP`；内部 23 个包。
- `internal/pkg` 只在**出现第二份调用**时才抽象，已按此拒掉 `httpx` / `errx` / 全量
  `jsonsafe` 迁移；现只保留 `jsonsafe`、`timex` 两个原语。
- `internal/upstream` 曾是 74 文件 / 23.7k 行，协议转换与养号活动两个**正交域**同居；
  growth 拆分已立项（ADR-018 草案待拍板），前置条件是先补行为级测试基线。
- 出站请求唯一入口 `internal/upstream`（R6）。R8 三条报文字符串**禁改名**：
  `wb2api-<ms>` conversationId、`chatcmpl-wb2api` 哨兵、三段式 UA——改名有风控风险。

### 2. 上游协议

- 出站 body 是 **AST 级重组**（unmarshal → 改写 → marshal），显式删除键只有
  `max_completion_tokens` / `tools` / `functions` / `tool_choice` / `response_format` 一类，
  其余原样透传。
- `/v1/responses` 复用 chat 管线做协议转换，upstream **零改动**；真机 Codex 未验证 = unknown。
- 结构化输出：真机一发实测上游**认 `json_object`**（observation）；其余模型与 `json_schema`
  形态 = unknown。
- `/v1/models` 精简目录缺字段 ≠ 不支持：`supported_efforts` / `supports_images` 缺失一律按
  **未知**处理，禁 `!field` 判否。

### 3. 选号与成本（养号核心）

- 硬过滤 `credit_floor` 有**悬崖效应** → 软带（带内 ×0.5 降权）+ `pickReason` 四路径溯源
  （能回答「这个请求为什么落在这个号」）。
- 软带带宽 `20_000 token` 假设被真机**双峰分布推翻**：聊天 p50 = 762 token；评测单次
  30–32 万 token、单次约 4.4 credit（是假设带宽的 15 倍）。候选 A 分口径（推荐）/ B 单 P50 /
  C 维持——**待拍板**。
- pace 模式按「每小时剩余额度相对池中位」分档 `[1,2]`，默认关；生产开启待人工决策。
- EWMA α=0.1 对单次失败几乎不敏感，连败 5 次才出池 → 抖动号会被下一请求反复打中
  （REQ-pool-failure-window 的由来）。
- 成本 tier = **inference**（少量 credit 样本外推）；USD 折算 = inference；延迟分位 =
  **derivation**（固定分桶插值）。三者不得当 observation 展示。

### 4. 安全

- 空 `api_key` 只在**回环监听**下合法；非回环 + 空 key 直接拒启（`1c0b89d`）。
- 已落地：凭证 ACL（icacls）、常量时间密钥比较、受信任代理判定 XFF、入站 body 上限、
  禁 HTTP/2；面板 Bearer + HttpOnly + CSRF + 限流；显式代理 **fail-closed**（配错 = 该号全失败）。
- 仍欠：`image_edited.png` 里的 key 仍在 GitHub 历史（历史清除未做）；凭据静态加密未做
  （与插件共读 auth 文件冲突，需单独决策）。

### 5. 观测与四态纪律

- unknown 是**一等实体**：带 `revision` + `requires`，用过期 revision 调 Resolve 必须报错；
  **推断不能消解推断**。
- reqlog 已加 `kind` 三值（chat / probe / farming，后两个为占位词表）+ `session_fp` /
  `agent_kind`，`/status` 出 `agent_profile` 聚合块。
- 「该号不可用」是**混合态**，必须拆成硬观察（上游 402 / 禁用）与推断判定（成本 tier、健康度）。
- 未覆盖 = unknown，不是 absence；否定断言必须穷尽证据源。

### 6. 工程与部署

- `deploy-prod.ps1` 一条命令完成「备份 → 等端口释放 → PE 预检 → 改名替换 → 启动 → 健康轮询 →
  冒烟 → 失败回滚」；退出码 `0/1/2/3/4` 语义严格区分（1=未生效且旧版在跑，2=已自动回滚，
  4=生产可能不可用）。脏工作区 `-Build` 拒绝；改脚本先跑 rehearsal（6 场景 53 断言）。
- 门禁 `pre-commit` 11/11；depth 棘轮 `1070/2/7/74/1827`；上下文预算 14805 token，只许下调。
- 已机器化的踩坑：PS 5.1 引号/编码假红、覆盖被占用 exe 必须改名、`cmd` 重定向产生孤儿 launcher、
  `gofmt -l` ≠ `go fmt -l`、`-coverpkg` 目录式写法静默报 0%、`go:embed` 资源无内容指纹需显式 no-cache。
- 实测口径：go1.27.3；30 包 = **26 ok + 4 无测试文件**（bench / harnessrun / signin / trial）。

### 7. 产品判断

- 三护城河（实测成本分层 / 健康治理 / 决策溯源）经八维对比为同类空白；magpie 强在额度记账与
  路由排序，与本项目正交，已采纳 3 项并落地。
- harness 产品化：**短期不建议**（V3-14 结论），治理体系可提炼为开源模板。
- 明确不做：多租户计费/兑换码/OIDC、多 provider、提示词日志留存、面板多语言/主题、
  账号自动发现、intent routing。
