# 度量基线（F5）— 先攒数字，再谈加层

> REQ-harness-engineering-2026-10-19 §五 F5。**这是 P0 里唯一直接对应 HarnessTax 结论的需求**：
> harness 对成功率影响仅 ±2–5%，对成本影响可达 5×，成本主源是首调用上下文。
> 所以「要不要再加一层治理」必须先用数字说话，不许凭感觉堆层（Handbook 三大反模式之首：过度配置）。
>
> **当前状态：2/5 组**（2026-10-19 / 2026-10-20）。剩下 3 组是**待补**，不是 0——没记的数字一律按
> **unknown** 处理，不许写成「没有成本」或「没影响」（四态纪律）。

## 一、记账口径（先定口径，再填数）

| 字段 | 怎么取 | 四态 |
|---|---|---|
| 常驻治理层 token | `scripts/check-context-budget.ps1` 的输出（CJK÷1.5 + 其余÷3.8） | derivation（估算，非 tokenizer 实测） |
| 首调用上下文 token | = 系统提示 + 工具 schema + 常驻治理层 + 首轮消息。**本仓没有计数器** → 只能记「常驻治理层」这一项，其余记 unknown | 部分 unknown |
| 总 token | 一次任务从开工到收工的全部消耗。本机无计数器；可用替代口径：面板 `/status` 的统计，或 provider 返回的 usage | 待定（先留空） |
| 轮次 | 工具调用批次数（一次消息里的多个调用算 1 轮）。**含重试**要单独注明 | observation |
| 耗时 | 墙钟时间。粗略到「分钟」即可 | observation |
| 是否一次通过 | 门禁首跑是否全绿；红了几项、分别是什么 | observation |
| 真问题命中 | 治理层**报出的**、需要人动手修的问题数（与「误报」分开记） | observation |

**误报与真问题的分界**（记的时候就要分开，否则数字没法用）：
- 真问题 = 报出来之后**确实改了东西**（断链、漂移、缺段、预算回退）。
- 误报 = 报出来之后确认是脚本判据不严谨，需要**改脚本**才能消掉。

## 五、这批数字怎么用（两周后的判据，先写死，免得到时候改口径）

统计 F1 + F2 在这两周里报出多少**真问题**：

- **真问题 ≥ 1 且误报 ≤ 1** → 保留，并按命中类型决定要不要补检项 4/6（ADR 编号、changes summary）。
- **误报 ≥ 3** → 先修判据，不许靠「习惯了这个红」继续用（那等于门禁失效）。
- **零命中** → **停手**。说明治理层目前自洽，后续投入应停止（PRD §一 Q4 的「不做」结论），
  不要往下加漂移审计 / 红线审计 / 评测集。

**反向纪律**：不许为了让数字好看而改判据或改基线。基线只许下调（F2 脚本强制），
真问题数不许把「误报」算进去。
