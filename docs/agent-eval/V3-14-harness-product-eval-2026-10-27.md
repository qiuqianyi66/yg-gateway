# V3-14 · Harness 产品化可行性评估（2026-10-27）

> 只评估不立项。结论先行：**短期不建议产品化**，但治理体系可提炼为开源模板。

## 一、为什么要评估

YG Gateway 的治理体系（四态语义纪律 / 机器棘轮 / Seen 计数 / 判据文化）
在本仓实战中自证有效（拦下 4 类真问题），且同类开源项目中无对标。
harness runner（cmd/harnessrun）是潜在的对外形态。
本评估回答：这套体系能不能独立产品化？

## 二、已实证的有效组件（本仓）

| 组件 | 机制 | 实战效果 |
|---|---|---|
| 四态语义 | observation / derivation / inference / unknown 分离 | 防止把 2 个样本的推断当事实（养号决策） |
| 机器棘轮 | check-depth / check-context-budget 只许收紧 | 防止代码体量膨胀（app.js 4378→4278） |
| Seen 计数 | 同一类坑第 2 次出现即升级为规则 | L-15 否定断言纪律 |
| pre-commit | 11 项全量门禁 | 提交前自动验证 |
| 变更追踪 | REQ + ADR + summary 三件套 | 每改动有留痕 |

## 三、产品化的可行路径

### 路径 A：独立开源模板（推荐）
- 形态：GitHub repo，包含 scripts/ + .harness/rules/ + AGENTS.md 模板
- 目标：给其他 Go 后端项目复用
- 成本：低（本仓已沉淀，提炼即可）
- 收入：无（开源，品牌价值）

### 路径 B：SaaS 服务（不推荐）
- 形态：Web 面板，各项目接入
- 问题：①与网关主线无关 ②多租户/计费是红线 ③运维成本高

### 路径 C：CI 插件（中等）
- 形态：GitHub Action，跑本仓的 check-* 脚本
- 成本：中（需要通用化，去掉网关特定逻辑）
- 收入：无（开源 Action）

## 四、风险与卡点

1. **治理体系强耦合本仓**：四态/棘轮是为网关养号决策设计的，其他项目不一定需要
2. **文档成本高**：AGENTS.md + rules + LESSONS 是核心资产，但新人上手门槛高
3. **无对标验证**：本仓是唯一用户，无法证明通用性
4. **主线仍是网关**：产品化会分散精力（违反 V3 定位）

## 五、结论

**短期（V3 周期内）：不产品化。** 主线仍是网关稳定性 + 账号池运营。

**中期（V4 后）：可做路径 A（开源模板）。** 前提是：
- 治理体系在本仓再跑 2-3 个月，验证长期有效性
- 提炼时去掉网关特定逻辑（四态/棘轮通用化）
- 写 README 说明适用场景（不是所有项目都需要）

**明确不做**：路径 B（SaaS）——与红线冲突（多租户/计费）。
