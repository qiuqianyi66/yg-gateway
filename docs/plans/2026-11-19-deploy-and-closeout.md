## 三、四个候选方案

### F1｜方案 A：部署生产 + 打 tag（**推荐**）

- **做什么**：跑排练 → `deploy-prod.ps1 -Build -Feature deploy-2.3.0` → 打 `v2.3.0` tag 并推
- **完成态**：`/healthz` 返回真实账号数、`/v1/messages` 缺 model 返 400、流式失败返 `event: error`、部署报告 JSON 落盘且退出码 0
- **风险**：秒级中断（`cmd` 重定向重启）；新版运行时问题 → 脚本自动回滚（退出码 2）
- **回滚**：`backup_path` 自动备份；退出码 2 = 已回滚，4 = 旧版没回来（需看 stderr）
- **工作量**：排练 ~10min + 部署 ~5min + 冒烟复查 ~10min ≤ 1h
- **前置**：**用户授权重启 7863**

### F2｜方案 B：真实 Anthropic SDK 联调

- **做什么**：装 `anthropic` Python SDK，用 `/v1/messages` 打本机实例，验证 SDK 能否消费流内 `error` 事件与 `stop_reason`
- **完成态**：SDK 在失败场景抛异常而非静默返回空内容
- **风险**：低（空池实例，零积分）
- **价值**：消解记录里最后一块「真实客户端未验」
- **但**：仍不能替代 F1 —— 它证明的是"客户端能正确理解"，不是"生产已修好"
- **工作量**：≤2h

### F3｜方案 C：重构 `message_start` 时序

- **做什么**：现在 `message_start` / `content_block_start` 先于失败发出（客户端已收到 `message_start` 才发现失败）。彻底修需"先探测上游再开流"
- **风险**：**中-高**，动流式核心时序
- **价值**：低-中（客户端已有 `event: error` 兜底，只是时序不够干净）
- **不推荐**：收益不抵风险，且会碰 R8 邻近区域

### F4｜方案 D：继续补覆盖率

- **现状**：`internal/server` 83.9%，零覆盖只剩 3 个一行转发
- **可做的**：转其他包的低覆盖函数（`interceptWriter.Write` 66.7%、`usageTotals` 50% 等）
- **价值**：**边际递减**。83.9% 已高于多数 Go 项目；继续补更多在测"分支是否存在"而非"行为是否正确"
- **不推荐**：除非有具体缺陷线索，否则属于"为了有活干而找活"
