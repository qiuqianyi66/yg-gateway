# REQ — scheduler 同族任务互斥（P2-5）

## 必要性

面板的「立即执行」按钮走 `go Scheduler.RunXxxNow()`（`internal/panel/panel.go:687-733`），
而排程主循环走 `runBatch` → 同样是 `RunCheckinNow` / `runActivity` / `runKeepalive` 这些入口。
两条路径没有互斥：排程正在跑签到（20+ 个号、每号两次上游调用）时点一下按钮，就会**再并行跑一整趟**。

为什么这不只是「多打几个请求」：签到 / 活跃上报 / 黑猫都是**按次计**的上游调用，
账号池的长期存活直接取决于请求形态（本项目 R8 与养号策略的全部前提）。
重复并发触发等于把这些计次调用翻倍，且失败日志会交错、难以归因到具体一次执行。

2026-10-22 审计把它记为 P2 并留待下一轮（「无数据损坏证据」）；本轮把它作为唯一问题处理，
判据不是「数据损坏」，而是「同族并发重入 = 上游请求量翻倍，且无法用日志区分两趟」。

## 需求

同一任务族（签到 / 旅行 / 活跃 / keepalive / 黑猫 / 快照 / 余额刷新）在同一时刻只允许一趟执行；
撞上时**后到者直接跳过并留一行日志**，不排队（排队会在前一趟结束后立刻补跑第二趟，等价于把
并发重入改成串行重复）。不同族之间仍并行（`runBatch` 的并行派发语义不变）。

## 验收（GWT）

- Given 排程那趟正卡在某账号的上游请求里 → When 面板手动触发同族 → Then 手动那次立即返回、
  **不产生第二次上游请求**，且日志出现「同族任务已在执行，跳过本次触发（P2-5）」。
- Given 上一趟已结束 → When 手动触发同族 → Then 正常执行（锁是「占用中跳过」，不是永久拒绝）。
- Given 两趟确实串行 → Then `/v2/report` 的并发峰值恒为 1。

## 不做

- 不改 `runBatch` 的并行派发（不同族仍并行，慢族（活跃上报要睡数分钟）不挡其他族）。
- 不引入队列 / 重试 / 优先级：跳过 + 日志已足够表达「这趟有人在跑」。
- 不给 `RunStreakBonusNow` 单独上锁：它只由 `RunCheckinNow` 末尾调用（已在该族锁内），
  面板也没有它的入口（`panel.go` 实测只有 5 处 `RunXxxNow`）。
