## 七、清理过程中牵出的 🔴 真实回归（已修复）

评审初稿把「表头常量重复定义」和「未使用的 `week` 变量」当作 🟢 次要项打算顺手清掉。
清理动作本身引入了两个**破坏性回归**，均由既有测试当场抓出：

### 7.1 提出模块级常量 → 测试 ReferenceError

`frontend_test.go` 用 `indexOf` 定位代码段喂给 `node` + `vm`，两个用例分别切：

- `TestAppJSExpirySortedByExpiry`：`function expBatches` → `async function loadExpiry`
- `TestAppJSExpirySnapshotRenders`：`function renderExpirySnapshot` → `async function loadExpiry`

两段**没有公共前导区**（后者的起点在前者内部），因此模块级常量**不可能同时落进两段**。
把 `head` 提成模块级 `EXP_HEAD` 后，切片外的引用直接 `ReferenceError: EXP_HEAD is not defined`。

**结论：不修（保留重复）**。这是切片契约下的必然代价，已在两处代码注释写明原因，
并注明「本注释刻意不写出函数声明字面量」防止下一个人误改。

### 7.2 注释里写函数声明字面量 → 切片被从中间切断

第一次修复时为说明原因，在注释里写了完整函数声明字面量
（`` `function renderExpirySnapshot` → `async function loadExpiry` ``）。
结果 `indexOf` 先命中**注释**而不是函数本身，切片起点落到注释处、终点落到真实
`loadExpiry` 之前，代码段被从函数中间截断 → `SyntaxError: Unexpected end of input`。

**修复**：注释改为描述性表述（"本快照渲染函数"、"loadExpiry"），不含完整声明字面量。
验证方式：对四个标记做全文计数，各应为 **1 处**（即真实函数定义）。

### 7.3 教训

用 `indexOf` 做代码切片是脆弱的契约，它把**整个文件的文本**都变成测试依赖——
注释、字符串字面量都可能成为隐式锚点。清理"重复"之前必须先确认重复是不是契约要求的。

## 八、真机截图牵出的 3 项信息设计缺陷（已修复）

代码层与单元测试都看不出来（断言只关心结构与转义），截图后才暴露：

| # | 缺陷 | 修复 |
|---|---|---|
| 1 | 列名歧义：第 3 列（21 天）叫「剩余」、第 4 列（499）叫「该批」——「剩余」会被读成"剩余积分"而与第 4 列撞义 | 改为「距到期 / 该批积分」，并把列名结论钉进 `TestAppJSExpiryCardGrid` 防回退 |
| 2 | 快照版每行挂"仅最早一批，点「检查」看全部"，4 账号重复 4 次、零信息增量，且把行高从单行撑成两行 | 删除逐行提示（卡片头部 `expNote` 已有一次说明） |
| 3 | 日期列左对齐，列间空白把「2026-10-31」与「21 天」这对同一事实的数据拉开，视线需跨空白来回跳 | 日期改右对齐（它是"值"不是"标签"），值区连成一片 |

### 8.1 截图验证自身的坑

面板 `theme` 默认 `'auto'` 跟随 `prefers-color-scheme`，而 Playwright 默认 `colorScheme: 'light'`。
第一轮"暗色"截图实际拿到的是亮色主题，两张图 sha256 完全相同才发现。
修复：按 `colorScheme` 分别建 context，并断言 `body` 计算样式
（dark `rgb(12,14,20)` / light `rgb(244,245,248)`）确认主题真的切换。
