# REQ-001 harness runner（V3-9）

## 必要性（阶段 0）

1. **真实问题**：GOLDEN-TASKS.md 定义了 5 个金样任务用来评测 agent 在本仓的干活能力，但目前靠人工跑、人工评分、人工写 run-*.md。机器可判的评分点（go test 绿、gofmt 干净、变更目录齐全、pre-commit 通过）也要人工一条条跑，费时且容易漏。
2. **不做会怎样**：金样任务重放成本太高，导致规则变更后没人重放，第三个棘轮（agent 行为）形同虚设——写了但没人执行。
3. **现状是否已变**：GOLDEN-TASKS.md 已有 5 个任务的评分点定义，首次 run 被子 agent 配额阻塞（run-2026-10-24.md）。机器可判的部分现在全靠手动跑命令。
4. **更便宜手段**：把机器可判的评分点写成一个命令行工具，一条命令出结果。人工评分点（文档找齐没找齐、否定断言做没做）还是人工来，但机器部分自动化。

**结论：做**（L2：单命令行工具，覆盖机器可判的评分点）。

## 范围

| 编号 | 功能 | 验收（Given-When-Then） |
|---|---|---|
| F-1 | `harnessrun list` | Given 运行 harnessrun list；When 列出 5 个金样任务名称与一句话描述；Then 输出 T1-T5 及各自主题 |
| F-2 | `harnessrun check T1` | Given T1 任务完成；When 跑机器可判评分点检查；Then 输出：go test 是否绿、gofmt 是否干净、变更目录是否存在 |
| F-3 | `harnessrun check T2` | Given T2 任务完成；When 跑机器可判评分点检查；Then 输出：REQ 是否含必要性段、pre-commit 是否通过 |
| F-4 | `harnessrun check T5` | Given T5 任务完成；When 跑 deploy-rehearsal.ps1；Then 输出 53/53 是否通过 |
| F-5 | `harnessrun report` | Given 各任务评分完成；When 生成报告；Then 产出 run-YYYY-MM-DD.md 模板，含各任务得分与机器检查结果 |

## 不做（显式排除）

- 不做自动启动 agent 会话（这个概念上就不对——agent 评测是人工/外部 agent 来跑的，我们只做评分辅助）
- 不做自动评分人工可判的部分（T3 文档漂移、T4 否定断言纪律，这些还是人工）
- 不做 Web UI（命令行足够）

## 回滚路线

删掉 `cmd/harnessrun/` 和本变更目录即可。
