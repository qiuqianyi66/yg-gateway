# REQ-001 OpenDesign 源码学习吸收计划

## 必要性（阶段 0）

1. **真实问题**：对照 OpenDesign（104k star 的 AI 设计 Agent 编排器）源码后，发现 YG Gateway 在工程纪律上有 6 个可吸收的改进点——R6 红线靠 review 人盯、错误分类缺确定性标签、改上游代码要真打上游验证、SSE goroutine 回收路径未验证、账号健康靠被动等待、reqlog 缺请求指纹。
2. **不做会怎样**：R6 违规不能机器拦截，一次随手 http.Get 就绕过重试/熔断；误判错误时日志看不出可靠性；改 errors.go/sse.go 后要真烧 token 验证；死号要等用户请求才发现。
3. **现状是否已变**：OpenDesign 源码逐行读过、YG Gateway 代码逐行对照过，问题成立。
4. **更便宜手段**：先做 P0 两项（R6 机器检查 + evidence_level 标签），成本最低收益最快；其余按优先级推进。

**结论：做**（L2：6 个子任务按 P0→P1→P2 分批交付）。

> 来源：2026-10-26 对 github.com/nexu-io/open-design（104k star）的源码级对照分析。
> 不是照搬代码，是吸收思想——OpenDesign 是消费端多 CLI 编排器，YG Gateway 是服务端单上游账号池，上下文不同，只取可移植的工程思想。

## 背景与必要性

动工前研究收口（实证，非转述）：

- OpenDesign 的 mocks/ 用 179 条 Langfuse 录制 traces 做 PATH-overlay 回放，改 parser 后 diff golden events，零 token 成本。YG Gateway 现在改 errors.go/sse.go 后要真打 CodeBuddy 验证。
- OpenDesign 的 run-failure-classification.ts 有 evidence_level 和 repair_owner 维度。YG 的 errors.go 只分类"是什么错误"，缺"有多确定"和"谁来修"。
- OpenDesign 的 RuntimeAgentDef 有 authProbe/compatibilityProbe 主动探测。YG 是被动等请求失败才知道账号死了。
- OpenDesign 的 pnpm guard 机器检查 run start choke point。YG 的 R6 红线（出站请求集中 upstream）靠 review 人盯。
- OpenDesign 的 supervisor 有 owner death → 子进程树回收。YG 的 R9（goroutine 回收）需要验证 SSE 路径。
- OpenDesign 的 stable-sections.ts 对 prompt 各 section 算 hash 归因 cache miss。YG 的 reqlog 缺请求指纹。

## 分级

整体 L2（业务逻辑增强），其中 mocks 回放和 R6 机器检查偏 L1（工程纪律强化）。

## 任务清单（按优先级排序）

### P0-1 R6 红线机器检查

**问题**：AGENTS.md R6 写了"出站请求集中 internal/upstream，禁其他包直连上游"，但靠 code review 人盯，没有机器检查。

**受影响文件**：
- `scripts/pre-commit.ps1`（加检查项）
- 可能触发：`internal/server/`、`internal/panel/`、`internal/scheduler/` 里如果有直连 CodeBuddy 的 http.Get/http.Post

**Given-When-Then 验收**：
- G1：Given 一个违反 R6 的包（比如 internal/scheduler 里直接 http.Get 到 codebuddy 域名），When 跑 pre-commit.ps1，Then 报错并指出违规文件。
- G2：Given 正常代码，When 跑 pre-commit.ps1，Then 检查通过。
- G3：检查脚本本身被纳入 pre-commit 门禁，本地与 CI 同源。

**验证方式**：写一个故意违规的测试文件，跑 pre-commit 确认报红，然后删掉。

**风险**：可能误报——有些包可能有合法的出站请求（比如登录回调、健康检查）。需要白名单。

**回滚**：pre-commit.ps1 里删掉新加的检查段即可，纯脚本改动。

### P0-2 错误分类加 evidence_level 标签

**问题**：ErrKind 只回答"是什么错误"，不回答"这个分类有多确定"。结构化 code 判定（如 `"code":11102`）是高置信，关键词子串匹配（如 `"rate limit"`）是中置信，status code 兜底是低置信。误判时日志里看不出可靠性。

**受影响文件**：
- `internal/upstream/errors.go`（Error 结构加 EvidenceLevel 字段，Classify 里打标）
- `internal/server/logging.go`（reqlog 记录 evidence level）
- 测试文件

**Given-When-Then 验收**：
- G1：Given 一个 400 + `"code":11102` 响应，When Classify，Then 返回 ErrModelBlocked 且 EvidenceLevel=high（结构化 code 判定）。
- G2：Given 一个 200 + body 含 "rate limit"，When Classify，Then 返回 ErrSoftRate 且 EvidenceLevel=medium（关键词匹配）。
- G3：Given 一个 500 响应，When Classify，Then 返回 ErrServer 且 EvidenceLevel=low（status 兜底）。
- G4：reqlog 日志行携带 evidence_level 字段，缺失时为空（三态）。

**验证方式**：单元测试覆盖各判定路径的 evidence 标签。

**风险**：低——只是加标签，不改变现有分类行为。

**回滚**：Error 结构加 omitempty 字段，回滚后旧日志行多出的字段被忽略，双向兼容。

---

### P1-1 mocks 录制回放（零 token 测试）

**问题**：改 errors.go / sse.go / client.go 后，验证要真打 CodeBuddy，烧 token 且不稳定。OpenDesign 的 mocks/ 用录制的 JSONL 回放。

**受影响文件**：
- `internal/upstream/testdata/`（新增 fixture 目录）
- 新建 `internal/upstream/mocks_test.go`（httptest.Server 回放）
- 录制脚本（可选：一个工具把真实响应存成 fixture）

**Given-When-Then 验收**：
- G1：Given 一批录制的 CodeBuddy 响应 fixture（JSON 格式），When 用 httptest.Server 回放，Then 网关的 Classify 输出与预期一致。
- G2：Given 修改后的 sse.go 流解析，When 回放同一个 fixture，Then diff 输出的事件序列，发现回归时报红。
- G3：fixture 带元数据（captured_at、upstream_version），记录这条 fixture 是哪个 CodeBuddy 版本录的。

**验证方式**：先录 3-5 个典型响应（成功、429 限流、402 余额不足、SSE 流、错误信封），建 mock server 回放测试。

**风险**：fixture 会过时——CodeBuddy 协议变了 fixture 就失效。需要标注录制时间，定期重录。

**回滚**：测试文件和 fixture 目录，删掉即可。

---

### P1-2 SSE goroutine 回收路径检查

**问题**：R9 红线"goroutine 必须有回收路径"。SSE 流式响应有个经典问题：客户端断连后，上游 HTTP 响应体有没有被正确关闭？读 SSE 的 goroutine 有没有退出？

**受影响文件**：
- `internal/server/handler.go`（SSE 透传路径）
- `internal/upstream/sse.go`（读流逻辑）

**Given-When-Then 验收**：
- G1：Given 一个正在进行的 SSE 流，When 客户端断开（r.Context().Done() 触发），Then 上游 resp.Body 被 Close()，读 SSE 的 goroutine 退出，没有泄漏。
- G2：Given 一个 SSE 流中途上游返回错误，When 读流 goroutine 检测到错误，Then 正确转发错误给客户端，goroutine 退出。
- G3：如果发现泄漏，修复并加测试证明。

**验证方式**：先读代码确认现状，发现问题再修；没问题就记录"已检查无泄漏"。

**风险**：低——这是检查项，不是功能改动。

**回滚**：无改动则无需回滚。

---

### P2-1 主动探测（账号健康巡检）

**问题**：现在是被动等请求失败才知道账号死了。OpenDesign 的 authProbe 在版本检查后主动 spawn 一个轻量命令探测认证状态。YG 的养号调度有签到，但缺账号存活探测。

**受影响文件**：
- `internal/scheduler/scheduler.go`（加一个轻量探测任务）
- `internal/upstream/client.go`（加一个轻量探测方法，比如请求 models 列表或一个极短的 chat）

**Given-When-Then 验收**：
- G1：Given 一个账号入库，When 调度触发探测，Then 发一个极轻量请求确认账号可响应，记录结果到 pool。
- G2：Given 一个已死账号（session 失效），When 探测，Then 标记为不可用，不等到用户请求才发现。
- G3：探测流量不进 reqlog 的 kind=chat，而是 kind=probe（复用 reqlog-kind 的词表）。

**验证方式**：单元测试 + 集成测试（用 mock upstream）。

**风险**：探测本身可能触发上游风控——太频繁的轻量请求可能被当成异常流量。需要控制频率（比如每 30 分钟一次，而不是每分钟）。

**回滚**：scheduler 里的探测任务可以配置开关，关掉即回滚。

---

### P2-2 请求指纹追踪

**问题**：reqlog 记录了请求结果，但没有记录"这次请求跟上次比哪部分变了"。OpenDesign 的 stable-sections.ts 对 prompt 各 section 算 sha256，cache miss 时归因到具体输入。

**受影响文件**：
- `internal/reqlog/reqlog.go`（Event 加指纹字段）
- `internal/server/logging.go`（请求时算 hash）

**Given-When-Then 验收**：
- G1：Given 一个 chat 请求，When 记录 reqlog，Then 携带 system_prompt_hash、messages_len、tools_count、ua_version 四个指纹字段。
- G2：Given 两个只有 system prompt 不同的请求，When 记录 reqlog，Then system_prompt_hash 不同，其他字段相同。
- G3：缺失指纹字段时为空（三态），不影响旧日志行解析。

**验证方式**：单元测试。

**风险**：低——只是加记录字段，不改变请求行为。

**回滚**：omitempty 字段，双向兼容。

---

## 不做的（明写，免得下轮重提）

- 不引入 Electron/sidecar 多进程架构（YG 是单二进制零依赖）
- 不做 30+ CLI 适配抽象（只接 CodeBuddy，过度抽象是负担）
- 不做 prompt 双轨灰度（不需要）
- 不做用户指导文案体系（auth.ts 那套是产品 UI 层的事）

## 实施顺序

1. P0-1（R6 机器检查）→ 最低成本，立刻有收益
2. P0-2（evidence_level 标签）→ 低改动
3. P1-2（SSE goroutine 检查）→ 读代码确认，可能不改
4. P1-1（mocks 回放）→ 中等成本，解决痛点
5. P2-1（主动探测）→ 需要设计频率和风控
6. P2-2（请求指纹）→ 跟 reqlog-kind 合并做

## 验证总闸

每个子任务完成后跑：

powershell -NoProfile -File scripts/pre-commit.ps1
go test ./...
go vet ./...
gofmt -l ./cmd ./internal
