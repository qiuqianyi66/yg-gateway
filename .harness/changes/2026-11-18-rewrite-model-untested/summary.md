# rewriteModel 主路径零覆盖 + 一个实测确认的精度损失

日期：2026-11-18
提交：`<待填>`
上一提交：`a1c5144`

## 一、问题

`logging.go:259 rewriteModel` 覆盖率 **0.0%**。它在 `chatCompletions` 的主请求路径上，
作用是**改写 outbound body 的 model 字段**：客户端可能发 `vendor/alibaba/glm-5.2`
这类带前缀的名字，网关要把它换成裸模型名 `glm-5.2` 再打上游。

零覆盖意味着：这个每请求都跑、直接改客户端报文的函数，没有任何测试。

## 二、四条防护（两条是安全阀）

| 条件 | 行为 | 为什么 |
|---|---|---|
| `len(body)==0 \|\| bare==""` | 原样返回 | 没东西可改 |
| body 不可解析 | **原样返回** | 这是安全阀：不能因为网关解析不了就 400，上游可能能处理 |
| `model` 不存在 / 不是 string / 已等于 bare | 原样返回 | 省一次 Marshal（热路径） |
| 其余 | 改 model 后 Marshal | 正向路径 |

第二条单独拎出来：`rewriteModel` 的注释写明「不二次错误化」。如果这里改成返错，
一个上游本可自行处理的请求会被网关先拒掉 —— 网关越权。

## 三、实测确认的精度损失（本批钉住，不改）

`rewriteModel` 用 `map[string]any` 往返，所有 JSON 数字变 float64。
超出 2^53 的整数会丢位：

```
seed: 1234567890123456789  →  1.2345678901234568e+18
```

这不是本批引入的，是既有实现的结构性限制。**为什么只钉不改**：

1. 实际影响面小：会被影响的是客户端 body 里的大整数字段（典型是 `seed`）。
2. 真修要换成 `json.Decoder` + `Token` 流式改写（只改 model 值、其余字节原地透传），
   是一批独立的改动，且会动主路径 —— 需要单独设计与验证。
3. 更危险的做法是「顺手改成字符串替换」，那会在 body 里匹配到 `messages` 内容中的
   `"model":"..."` 子串，把用户对话内容改坏。

用例 `TestRewriteModelNumberPrecisionIsKnownLoss` 的作用是**把现状固定**：
它断言「确实会丢」，并在真的不再丢时 `t.Skip` 提示更新说明。这样日后有人以为
它是无损的，会被这条用例拦住。

## 四、验证

| 项 | 结果 |
|---|---|
| 5 个防护子用例 | 全 PASS |
| 正向改写（model 改对 + messages/max_tokens 保留） | PASS |
| 精度损失探针 | PASS（日志确认 `1.2345678901234568e+18`） |
| `rewriteModel` 覆盖率 | 0.0% → **91.7%** |
| `internal/server` 包 | 82.6% → **83.1%** |

**91.7% 而非 100% 的原因**：唯一未覆盖分支是 `json.Marshal` 返回错误。该 map 由
**已成功 Unmarshal 的 JSON** 构造，Marshal 不可失败（代码注释也这么写）。这是
「不可达分支」，不是缺口。

## 五、能力边界

1. 只测函数本身，**没有走 `/v1/chat/completions` 端到端验证**「客户端发带前缀 model →
   上游真的收到裸 model」。那个衔接由既有 chatrun 测试间接覆盖，本批未新增。
2. 精度损失**未修**，仅钉住现状，见第三节。
3. 未验证 map 往返导致的 **key 顺序变化** 是否影响上游。Go 的 `json.Marshal` 对
   `map[string]any` 按 key 排序输出，所以顺序是可预测的；但若上游对字段顺序敏感
   （不应如此，JSON 规范不要求顺序），会有影响 —— **未验证，也不打算为它改代码**。
