## 一、必要性

换版脚本借 `cmd.exe` 做 stderr 重定向启动实例。启动失败时（坏 exe / 端口被占 / 上游拒绝启动）
那个 `cmd` 可能残留：`Replace-Binary` 的改名替换让它**无害**（只握着一个已摘链的 inode），
但它会一直累积，而且让「到底有没有进程在跑」的排查变脏——2026-10-16 那次「不支持的 16 位应用
程序」模态框事故就留下过一个卡住的 `cmd`。

## 二、判据（三条全中才杀，避免误伤）

1. 进程名是 `cmd.exe`；
2. 命令行里出现**目标 exe 的完整路径**（我们的 launcher 一定带它，别人的 shell 不会）；
3. **父进程已不存在**（孤儿）。

刻意不用「按名字杀」或「按创建时间杀」：本机多会话共用，那两种都会误伤人工 shell。

## 三、怎么验证的

### 3.1 把函数从脚本里**原样抽出**做双向实测（不手抄逻辑）

| 用例 | 构造 | 期望 | 实测 |
|---|---|---|---|
| 真孤儿 | 先建「父 pwsh → 子 cmd（命令行含目标路径）」，再**强杀父**；确认子仍存活且父已不在 | 函数返回 ≥1，子被杀 | ✅ 返回 1，子不存活 |
| 在用的 launcher | 父 pwsh 仍存活 | 函数返回 0，子**不被杀** | ✅ 返回 0，子仍存活 |

> 构造坑（记下来）：第一版用「父进程正常退出」来造孤儿，结果子进程被一起带走——
> 父子共享控制台，父正常退出会拆掉控制台。**必须强杀父**，子才留下来成为真孤儿。

### 3.2 全量排练（6 场景 / 53 断言）

`powershell -NoProfile -File scripts/deploy-prod.rehearsal.ps1` → **53/53 全过**，退出码 0
（A1 非 PE 零触碰 / A2 坏 PE 自动回滚 / B 替换生效 / C DryRun 无副作用 /
D 停服后替换失败也把旧版拉回 / E `-Build` 遇脏工作区拒绝）。说明新增步骤没有破坏既有路径。

### 3.3 `-DryRun` 仍然可用

`deploy-prod.ps1 -DryRun` → 退出码 0，只打印计划。

## 四、调用点（两处）

| 位置 | 为什么 |
|---|---|
| 第 2 步「停旧实例」之前 | 清掉上一轮失败留下的孤儿，避免与本次启动混淆 |
| `Invoke-Rollback` 里 `Start-Instance` 之前 | 回滚时避免旧 launcher 与新的启动命令抢同一个 exe / 端口 |

## 五、边界（明说）

- 只认 `cmd.exe`。若将来启动方式改了（不再借 cmd），这条要跟着改，否则变成**空操作**。
- 读不到命令行（权限/别的用户）→ **不判断、不杀**（保守优先）。
- 父 PID 被复用（PID 回绕）时可能把「父仍存活」误判成孤儿；概率极低，且命令行过滤把范围
  限制在「含目标 exe 路径」的 cmd 上，最坏情况是杀掉一个指向同一 exe 的残留 launcher。

## 六、回滚

`git revert <本提交>`。回滚后残留 launcher 不再被自动清理（无害，只是累积）。
