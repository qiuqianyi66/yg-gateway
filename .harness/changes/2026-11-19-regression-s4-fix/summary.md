# 2026-11-19 回归脚本 S4：从「永远不跑」到「真的测会话 RPM」

## 发现（两个缺陷，都是脚本自身的）

1. **S4 根本无法执行**。原逻辑 `if "S4" not in skip: skip.add("S4")` 把 S4 无条件加进
   skip，于是 `if "S4" not in skip_with_s4_default: s4_session_rpm(...)` 永假。注释写的
   「显式加 `--skip ""` 或 `--skip 其他节来开启`」在代码里不成立——**会话 RPM 限流这条
   防线从未被回归覆盖**。
2. **即使跑起来也是假通过**。原断言只数「有没有 429」。实测 21 线程直发时 15/21 先被
   全局准入拒掉（`server_busy`），只有 6 条进入业务层，会话窗口（rpm=20）根本凑不满；
   剩下的 429 只要来自 server_busy / key 级限流，断言照样 PASS。注释说「并发 6 线程」，
   代码却是 21 线程——注释与实现不符。

## 改了什么

`scripts/yg-regression-test.py`：

- 新增 `--s4` 显式开关（默认仍不跑，因为它会故意打上游冷却）；`--skip S4` 可强制关闭。
- `s4_session_rpm` 改为 **6 个 worker 抽取 21 个任务**（并发不超过 `global_max_in_flight`），
  保证 21 次都进入业务层、落在同一 60s 窗口。
- 断言改成**按错误码判定**：必须出现 `session_rate_limit`，不接受 `server_busy` 冒充。
- 未进入业务层的（503 / 连接异常 / server_busy）单独计数，够不到 21 就 `[skip]` 不判定，
  不再用「有 429 就算过」的弱判据。
- 原断言名「无挂死无超时」名不副实（只检查线程存活）：改名为「无线程挂死」，客户端侧
  连接重置/超时降为 `[obs]` 观察项（不同运行的差异过大，硬断言会 flaky）。

## 怎么验证

| 验证 | 结果 |
|---|---|
| `python -m py_compile` | exit 0 |
| 修前跑 `--s4` | `Counter({-1: 11, 200: 6, 429: 4})`，429 码未知 → 假通过 |
| 修后跑 `--s4`（21 次 / 6 并发） | `Counter({200: 20, 429: 1})`、`codes={'session_rate_limit': 1}`、进入业务层 21/21、耗时 24.1s，**PASS 2 / FAIL 0** |
| 副作用 | 跑完 `/status`：`cooling=0`，4 个账号全部 `cooling=false`（429 是网关自身会话限流，未污染上游） |

## 未验证 / 观察

- 修前那次运行有 11 条客户端连接重置（`-1`），**复跑两次均未复现**（一次 0 条、一次
  15 条 server_busy）。成因未定性，只记为观察：可能与被拒时机 + 连接复用竞态有关，
  不得写成「已确认缺陷」。
- `--s4` 会真打上游（免费模型、零积分），只在有账号余量时用；默认仍关闭。

## 回滚

还原该文件即可（`git checkout -- scripts/yg-regression-test.py`）。S4 回到「永不执行」，
其余节不受影响。
