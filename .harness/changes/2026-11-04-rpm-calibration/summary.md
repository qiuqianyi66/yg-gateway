## 背景

P1-1B 已把出站 RPM 硬闸做成可配置能力（`upstream.rpm_per_account` 默认 0 关），
但「若开启该设多少」没有证据——只有「不开不亏」（429 极低），没有「开了设多少
不误伤」。本校准用 8 天生产请求日志（requests-2026-10-28..11-04.jsonl）算
每账号真实分布，给出证据支持的开启建议值。

## 数据与方法

- 源：D:\yg-gateway\data\request-logs\requests-2026-{10-28..11-04}.jsonl
  （8 天，6191 条 chat 请求，10 个账号——全 kind = chat，探测类未入此日志）
- 脚本：`analyze_rpm.py`（本目录，可复跑）——每账号 60s 滑动窗峰值
  （对照 rpm.go rpmWindow=60s）、1s 槽位占用峰值（对照 rpmSlot=1s）、
  间隔 <1s 的请求对数（槽位约束会把这些对拉平到 ≥1s）。

## 结论（校准）

1. **建议开启值 `upstream.rpm_per_account = 40`**：覆盖 8 天全部**真实账号** 60s
   观测峰值（37）+ 小余量，开启后对观测流量零误伤（不引入额外等待）。
   防御更宽可用 50（顺带覆盖 `-` 桶 44 峰值）。
2. **1s 槽位影响可忽略**：真实账号间隔 <1s 的对数最多 68（占该账号 4.5%），
   每对最多 +1s——8 天累计延迟分钟级，峰值期突发被平滑是硬闸的本意。
3. **默认保持 0 关不变**：429 极低（此前 min-interval-calibration：生产账号 0 次
   429），「不开」仍是证据支持的默认；40 是「需要时直接开」的已校准值。
4. **unknown（显式标注）**：
   - 阈值对 chat 维度有效；/v1/models 等探测类请求不在 request-logs 内，
     若未来探测频率上升需重校（requires：全 kind 出站日志或探测频率观测）。
   - `-`/`?` 账号的请求是否携带 X-Machine-ID 未知（日志 account 缺失 ≠ 出站无头）——
     rpmWait 空头归 global 桶，若此类请求真的无头且量大，40 会卡 global 桶
     （requires：出站侧 X-Machine-ID 注入日志）。
   - 峰值来源（自动养号/回归/真实流量）未区分，阈值取覆盖全部观测。
