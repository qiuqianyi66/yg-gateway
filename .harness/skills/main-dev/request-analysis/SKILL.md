# 需求分析技能（YG Gateway）

将模糊需求转化为清晰技术任务，识别业务影响与技术风险，输出可直接进入编码阶段的需求分析报告。

## 触发条件

- "新增一个 xx 功能" / "给网关加一个 xx" / "改 xx 逻辑" / "xx 支持 xx"
- 收到任何新功能需求或变更请求，进入开发流程前
- **只要收到需求即触发，禁止跳过本技能直接编码**

## 执行流程

### Step 0: 模式与复杂度判定

**模式**：起草（缺口靠追问）/ 授权修改（只改指定范围）/ 只审校（不改源文件，输出问题位置+证据+影响+建议）。

**复杂度**：A 微调（局部文案/字段）/ B 模块级（单模块闭环）/ C 耦合（共享对象/跨模块责任）。

### Step 1: 需求解析

- **功能点**：动词+宾语，每个编号 F1、F2…
- **边界**：做什么 / 不做什么（排除项同样列出）
- **验收**：Given-When-Then，禁"体验良好"这类不可验证表述
- **承重墙**：本项目的承重墙是 **选号/冷却/熔断、凭证链路、出站改写管线、上游协议报文**——需求一旦触及，必须在影响分析里显式声明，且默认不改（R8 红线）

### Step 2: 影响分析

- **业务影响**：账号池/积分/调度语义是否变化
- **技术影响**：Go 分层（cmd/internal）、面板（go:embed + CSP）、配置（热生效 vs 装配期）、上游报文

### Step 2.5: 就绪度审查（8 维）

流程 / 状态 / 权限 / 字段 / 交互 / 异常 / 数据 / 验收，任一维含糊 → 补进影响分析或提问，禁止带缺口进编码。

### Step 3: 任务拆分

任务粒度 ≤4h，依赖关系明确。**上手既有工作先取证**：路径/文件名/数字/状态一律回查磁盘与 git，禁止凭对话记忆转抄。

## 澄清规则（frontier 提问）

含糊点攒成一轮带推荐答案的编号清单一次性问完（≤5 条），每条三要素（推荐 + 理由 + 影响）。问题能通过读代码/wiki 自己回答的**不要问**，写"已核实：`<路径:行号>`"。

## 本项目特有的裁决铁律

1. **出站报文不动**（R8）：`wb2api-<ms>` conversationId、`chatcmpl-wb2api` 哨兵、UA 指纹属于协议数据，改名有风控风险。需求若涉及"优化"这些，一律拒绝并说明。
2. **配置分两类**：热生效（api_key/soft_rate/脱敏开关）走 livecfg；装配期（body 上限/受信任代理/限流/base 覆盖）需重启。需求要明确新配置属于哪类。
3. **前端改动必重编译**（R13）：面板是 go:embed 单文件，改 app.js/index.html 必须 `go build`，否则线上不生效。
4. **测试必须有牙齿**：新增修复类测试需验证"还原 bug 后 FAIL"。
