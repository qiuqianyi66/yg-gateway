# 模板：代码审查（6 维 checklist）

> 用法：整段粘贴，替换 `<...>`。适用于阶段 6。L2 及以上**必须有独立复审**
> （另一会话 / 子代理 / 他人，只读）——自己写的 review 只能算自评审（L-16）。

---

审查对象：**<分支 / 提交范围 / 文件列表>**，改动意图：**<一句话>**。

## 审查前先做的事（不做就等于猜）

1. `git diff <base>...HEAD` 拿到**完整**改动面；不要只看对话里贴的片段。
2. 读 `AGENTS.md` 红线段 + `.harness/LESSONS.md` 索引，命中条目读正文。
3. 对每个"看起来可疑"的断言，**去代码里找证据**（file:line），不靠印象。
4. 涉及上游协议 / 出站报文的改动：对照 R8 逐字段核（`wb2api-<ms>` conversationId、
   `chatcmpl-wb2api` 哨兵、三段式 UA），任何"顺手改名"直接 🔴。

## 6 个维度（逐维给结论，不许合并成一段）

| 维度 | 具体查什么 |
|---|---|
| **1 正确性** | 边界（0/负/空/超大）、状态流转、错误路径、并发（锁范围、goroutine 回收 R9）、nil 安全 |
| **2 性能** | 锁竞争、每请求分配、上游请求量放大、O(n²)、热路径（`upstream/sse.go`、`server/chatrun.go`）新增开销 |
| **3 安全** | 凭证泄露（R1）、日志脱敏 R2（UID 只前 8 位）、XSS/`esc` 转义（面板）、路径穿越、越权、密钥比较走 `internal/httpauth`（R5）、入站 body 上限 |
| **4 一致性** | 与 `docs/` 接口与数据模型一致、术语一致、四态标注是否与 AGENTS.md 清单相符（推断别写成观察） |
| **5 可维护性** | 命名、抽象是否必要（有没有第二个消费者）、重复（能否用 `internal/pkg` 现有原语）、函数体量 |
| **6 架构合规** | 依赖方向（`check-boundaries.ps1`）、是否绕过 `internal/upstream` 直连上游（R6）、是否新增 go.mod 依赖（必须个位数） |

## 分级与处置

| 级别 | 含义 | 处置 |
|---|---|---|
| 🔴 阻断 | 红线 / 安全 / 数据错误 | 必须修，**禁止降级合入** |
| 🟡 主要 | 功能缺陷 / 性能风险 | **清零**才可过评审 |
| 🟢 次要 | 可维护性建议 | 记录即可 |
| 🔵 提示 | 风格 / 微优化 | 不阻塞 |

## 必查的机器证据（贴原始输出，不贴结论）

```powershell
gofmt -l ./cmd ./internal
go vet ./...
go test ./...
powershell -NoProfile -File scripts/check-boundaries.ps1
powershell -NoProfile -File scripts/check-depth.ps1
powershell -NoProfile -File scripts/pre-commit.ps1
```

测试是否"有牙齿"：新增/修改的测试**在还原 bug 时必须 FAIL**。只跑绿不算证据——
问一句"这条测试如果把修复回退，会红吗？"，答不上就是没牙。

## 输出格式

落 `.harness/changes/<feat>/review.md`，**按轮次分段**（第 1 轮 / 第 2 轮…），
不许用新一轮结论覆盖上一轮。每条问题给：

```
[级别] 文件:行 — 问题一句话
  证据：具体代码片段 / 命令输出
  建议：改法（能直接落地的最小改动）
```

结尾给：🔴 N 条 / 🟡 N 条 / 🟢 N 条 / 结论（通过 / 有条件通过 / 驳回）。
**评审-修复闭环 ≤ 2 轮**；第 2 轮仍不过 → 暂停并说明卡点。
