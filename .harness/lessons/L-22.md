# L-22 结论/方案前必须穷尽证据

**一句话**：只读部分代码就断言机制全貌、把未验证前提当事实推进，等于带幻觉汇报——不报错但误导决策。

## 场景（2026-10-28，Seen 1）

用户在排查「passthrough 模式下客户端 system 提示词不生效、推理出现未发送内容」：

1. 未核实 `X-Session-ID` 的头族归属（实为**账号级设备指纹头**，headers.go:136-143，防设备指纹漂移
   关联风控），就把它当「会话绑定头」给出「请求级派生换会话桶」方案——方案直接制造风控雷。
2. 未验证「Tea 的 conversationId 是本地生成还是上游签发」「渗漏是会话级还是账号级」两个前提，
   就定了「主线方案：Tea 每会话生成新 conversationId」——前提不成立则方案白做，且伪造上游
   签发 ID 有 R8 风控风险。
3. 出站管线 `prepareBodyAST`（payload.go:65-115）在方案给出**之后**才读全，此前对「网关是否
   删改 system」仅有部分证据。

## 根因

- 片段式阅读 + 推断当事实：读了函数名/注释片段就下机制结论，没读完「该函数所在头族/完整管线」。
- 方案可行性没做前提分解：把「外部系统行为」「他项目行为」当已知，未标 unknown + requires。

## 规则（已升级 AGENTS.md「事实语义纪律」）

1. 禁止只读部分引用点/子函数就断言机制全貌——读到能回答「为什么」为止；
2. 方案依赖的每个前提（他项目行为 / 外部系统 / 未实测语义）必须显式标 unknown 并写明
   `requires`，禁止把未验证前提当事实推进；
3. 提交结论前逐条自检：每句关键断言必须有代码或实测出处；没有 → 标 unknown 或继续查。

## 防法

结论/方案出口前三问：

- 我断言的这个机制，对应的代码路径**全部**读完了吗？能回答「为什么」吗？
- 方案每个前提的出处是什么？是 observation 还是推断？推断的前提有没有标 unknown + requires？
- 把这些断言换个读者复核，他会因为哪一句没出处而无法验证？
