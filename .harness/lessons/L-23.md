# L-23 经典脚本顶层 let/const 的 TDZ——`typeof` 挡不住

**一句话**：`typeof x !== 'undefined'` 只对**未声明**变量安全；对 TDZ 中的 `let/const` 照样抛 ReferenceError。

## 场景（2026-11-04，Seen 1）

面板拆分组件后，`app.js` 的 `visibilitychange` 监听注册在第 1028 行，而 `queueTimer`
是顶层 `let`、声明在第 1141 行。代码里写了「用 typeof 守卫避免声明前触发」——实测浏览器
首屏即抛 `Cannot access 'queueTimer' before initialization`。

同次另一例：`start()` 在第 1035 行被顶层调用，而 `US_DIMS/US_DIM_TABS` 在第 1246 行
才求值 → `loadOverview → loadUsage` 命中 TDZ，用量页首次进入即「读取失败」，且 catch 分支
又读同一个常量、二次抛错。

## 根因

- 误以为「typeof 是访问前检查」：TDZ 是**绑定已存在但未初始化**，typeof 一样要解析绑定。
- 组件拆分把「数据常量/状态」留在 app.js 后半段，但启动调用和事件监听在中段——经典脚本的
  顶层执行顺序就是文件顺序，没有「函数声明提升」的安全感。

## 规则

1. 顶层 `let/const` 在被任何监听/启动代码引用前**声明上提到文件顶部状态区**，别留后置声明；
2. 启动调用（`start()`）必须放在整份脚本**末尾**，不许在中段顶层调用；
3. 禁止写 `typeof x` 形式的 TDZ 守卫——要么声明提前，要么用 try/catch 包真意图。

## 防法

- 机器检查（已落地）：`TestAppJSBootOrderGuards`（gamify_dom_test.go）——app.js 不许出现
  `typeof queueTimer`、queueTimer 声明必须在 visibilitychange 之前、文件末尾必须是 `start();`。
