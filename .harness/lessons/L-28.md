# L-28 标 unknown ≠ 登记待办

Seen: 1 ｜ 族系：与 L-26（校准 ≠ 机制）、L-22（结论前穷尽证据）同属「吸收不留尾巴」元主题 ｜ 状态：规则（REQ 必设「不做清单」段）

## 坑

REA 深挖时确认「单账号在途并发闸」未实现，但理由是「magpie 自己也标 unknown」——
于是把它写成 unknown 就收工了。几周后用户追问「magpie 的东西你只学到这么一点点」，
才重新发现这个洞；同期 magpie 的 8 天保活周期被（正确地）否决，连带把「保活错峰」
整个方向也弄丢了。两处都是**知道未吸收、但没落成待办**，被「unknown」这个词吸收了。

## 判据

深挖/吸收类任务（对照外部项目逐点核对）中，任何**已确认未实现**的项，
必须落成可执行待办，而不是 unknown 字段或一句备注：

1. **理由**：为什么这轮不做（数据不足 / 策略冲突 / 优先级）——必须是真实约束，
   不能是「源项目也没做」这种转嫁；
2. **触发条件**：什么数据或什么事件出现时重新评估（例：8 天日志 derive 出在途分布）；
3. **登记位置**：写进 REQ/PLAN 的「不做清单」（含理由 + 触发条件），并过检项 [10]
   引用断链检查——**不做清单里的一条，和做了的一条，同样需要可审计**。

unknown 只用于「不知道」（缺观察手段），不用于「知道了但没做」。
「标 unknown」是一个句号，待办是一个分号——吸收度追问的对象永远是分号。

## 修复

本次 F1/F2 落地时同步做：计划文件设「不做清单」段（挂 cron 观测 / 429 五分类 /
PII 占位符 / 8 天周期 / 共享 fetch helper / 并发阈值直抄 5-6，逐条带拒绝理由），
变更记录 summary 回引 REQ；并发阈值校准落为独立待办（数据源已指到 8 天日志，
结论将落 `.harness/changes/*-concurrency-calibration/`）。检项 [10] 的
changes 引用断链检查保证「不做清单」不会随文档漂移而消失。
