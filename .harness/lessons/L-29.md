# L-29 `-coverpkg` 目录式写法静默报 0.0%

Seen: 1 ｜ 族系：与 L-19（聚合脚本自证输入）、L-15（否定断言须穷尽）同属「零值不能当结论」元主题 ｜ 状态：规则（覆盖率度量一律写完整导入路径 + 剖面核对）

## 坑

给拆包后的 `internal/growth`（953 行、无本包测试）度量覆盖率，准备拿"零覆盖"当立项依据时：

| 命令 | 结果 |
|---|---|
| `go test ./internal/growth/ -cover -count=1` | `coverage: 0.0% of statements` |
| `go test ./internal/growth/ -coverpkg=./internal/growth/ -count=1` | 仍是 `0.0%`；`-coverprofile` 里 228 条语句计数**全为 0** |
| `go test ./internal/growth/ -run TestTravelStatusParsesFields -v` | PASS（证明代码确实被执行） |
| `go test ./... -coverpkg=yg-gateway/internal/growth -count=1` | growth **89.9%**（同一批代码、同一批用例） |

目录式（`./internal/growth/`，带斜杠、无 module 前缀）两次退出码都是 0、用例全绿，没有任何提示，
却把真实覆盖 89.9% 报成 0.0%。若不复核，"该包零覆盖"会作为结论写进方案——方向也许对，
但依据是假数字，后续"补测试"的收益评估和优先级排序都会跟着错。

## 判据

1. **度量跨包的覆盖一律写完整导入路径**：`-coverpkg=<module>/internal/foo`（module 从 `go.mod` 的
   `module` 行取，本项目是 `yg-gateway`）。目录式形态不用于度量。
2. **0.0% 先按口径问题处理，不按事实处理**：三步对照才判定真假 —
   ① `-coverprofile` 导出剖面，看目标包每条语句的计数列是否全 0；
   ② `-run <已知命中该包的单用例> -v`，确认 PASS；
   ③ 换完整导入路径重跑同一条命令看数字是否变化。
3. **「没有测试文件」与「覆盖率 0%」是两个事实**：前者用 `go list -f '{{.TestGoFiles}}' ./...`
   就能判；后者只认剖面。`scripts/check-depth.ps1:210-213` 有意把 `0.0%` 的包排除在
   `minCoverage` 之外（注释见 150-152），这个豁免同时让"口径假象"与"真零覆盖"看起来一样，
   所以判断「某包是否被棘轮管着」要看它有没有 `*_test.go`，不能看覆盖率数字。

## 修复

本轮落地：给 `internal/growth` 新增本包测试（`b0cbb5c`），覆盖率从"假 0.0%"变成真 93.4%，
该包因此重新进入 `minCoverage` 棘轮视野；度量口径写进 `docs/code-review/2026-11-10-baseline-and-plan.md`
的命令表，后续复查按上面的完整导入路径执行，避免下一个人重走一遍 0.0%。
