# 开发流程规范（YG Gateway）

> 定义"工作怎么走"。与 `编码规范.md`（怎么写代码）、`工程结构.md`（东西放哪里）配套。AGENTS.md 是总入口。
> 本规范从 tea 项目 harness 体系移植，按 Go 单仓库 + 内嵌前端的实际裁剪。

## 使用方式（触发条件）

- 🔴 **任何开发任务**：**先过阶段 0（必要性分析）**——不先回答「这事到底要不要做」，不许进入需求分析。
- **任何开发任务**：先按复杂度×风险分诊（Fast=轻量 / Guided=全流程 / Controlled=全流程+先确认）。
- **任何开发任务**：按「阶段 0 + 十阶段」流水线推进，阶段 N 的 Quality Gate 未满足禁止进入阶段 N+1。
- **任务启动前**：先 request-analysis 收口需求（F 编号 + Given-When-Then + 澄清规则）。

# 零、阶段 0：必要性分析（动工之前必须先回答）

> 由来：2026-10-17。当天盘点的 **14 项**待办里 **6 项经实测明确不做**、2 项降级、3 项等条件，
> **实际只动了 3 项**：其中两条是「写着未做、实际早做完」，一条的收益只有可用空间的 **0.13%**，
> 两条被设计/棘轮明确拒绝。直接开工的结果是：花几小时做一件不该做的事，还得再花时间回滚。
> **「待办清单」不是工作授权，它只是一批假设。**
> 当天完整裁定见 `docs/PLAN-necessity-review-2026-10-17.md`。

## 0.1 阶段 0 要回答的四个问题（写进需求文档「必要性」段）

| # | 问题 | 不回答的后果 |
|---|---|---|
| 1 | **要解决的真实问题是什么？**（引用观测/日志/用户症状，不是"清单上写着"） | 做完发现没人受益 |
| 2 | **不做会怎样？**（后果的可观测性 × 严重度：报错？还是静默浪费钱？） | 把"能看懂但没危害"当成缺陷 |
| 3 | **这件事的现状是不是已经变了？**（旧文档写的"未做/不存在/从不"是否仍成立） | 重复劳动（本仓已发生 ≥6 次） |
| 4 | **有没有更便宜的等效手段？**（机器核对代替重构、记录 unknown 代替实测、加指针代替搬运） | 用 3 小时解决 10 分钟的问题 |

## 0.2 结论只有四种，必须落一个

| 结论 | 判据 | 落到哪里 |
|---|---|---|
| **做** | 问题真实 + 不做的后果可见且有危害 + 无更便宜手段 | 进入阶段 1（需求分析） |
| **不做** | 问题不存在 / 危害可忽略 / 设计上已明确拒绝 | `docs/PLAN-open-items-*.md` 的「已决策不做」段，**或**当轮的 `docs/PLAN-necessity-review-*.md`（两者都要写理由与重评条件） |
| **等条件** | 卡外部输入（用户拍板 / 预算 / 域名 / 上游行为） | 列出「解锁动作」与「解锁后立刻能做的那一步」 |
| **降级做** | 完整方案太重，但其中一小块值得做 | 只做那一小块，并在变更记录写明**放弃了什么、为什么** |

## 0.3 硬约束

- 🔴 **不许用「清单上有」当必要性理由**。清单来自上一轮的假设，假设会过期。
- 🔴 **否定性断言（不存在/从不/全仓搜不到）必须穷尽证据源**（见 `AGENTS.md` 同名纪律 + `LESSONS.md` L-15）：
  写"不需要做"之前，先把能跑的命令跑了，别只读两处代码。
- 🟢 **阶段 0 的产出可以只有一段话**（L0/L1 小改动），但它必须在需求文档里看得见——
  机器校验：新增的 `docs/prd/REQ-*.md` 必须含 `## 必要性` 段（`scripts/check-req-necessity.ps1`，
  已接入 `pre-commit.ps1`；只对**本次新增**的 REQ 文件生效，存量文档不追溯）。
- 🟢 **结论是「不做」也是交付物**：它省掉的工作量就是收益，但必须写清重评条件，否则下轮会被重新提出。

# 一、十阶段流水线（阶段 0 之后的那十个）

| 阶段 | 名称 | 使用技能 | Quality Gate（退出条件） | Output |
|---|---|---|---|---|
| **0** | **必要性分析** | request-analysis | **四个问题有答案 + 四种结论落一个**（见「零」） | 需求文档的「必要性」段 |
| 1 | 需求分析 | request-analysis | 需求文档已产出且用户确认：范围边界明确（做什么/不做什么）、F-编号需求 + Given-When-Then 验收、非功能约束、影响分析完整 | 需求文档（PRD 级） |
| 2 | 方案设计 | request-analysis | 细化方案经用户确认（D-编号决策点已拍板），技术选型有依据，红线冲突清零 | 细化方案 + summary.md |
| 3 | 任务拆分 | request-analysis | 任务粒度 ≤ 4h，依赖关系明确 | 任务列表 + 执行顺序 |
| 4 | 编码实现 | coding-skill + biz-dev 专项 | 遵守编码规范，红线零违反，`go build ./...` 0 error | 可编译代码 |
| 5 | 单元测试 | unit-test-write + unit-test-ci | 核心逻辑测试覆盖（含牙齿验证），测试全绿 | 测试报告 |
| 6 | 代码评审 | expert-reviewer | 评审通过无 🔴 问题；门禁全绿 | 评审记录 review.md |
| 7 | 集成测试 | -（联调执行） | 端到端链路通过（真实账号/真实上游） | 集成测试报告 |
| 8 | 预发验证 | deploy-verify | 独立端口/目录验证通过（含冒烟） | 验证记录 |
| 9 | 上线部署 | deploy-verify | 二进制替换 + 备份 + 重启，冒烟通过 | 部署记录 |
| 10 | 线上观测 | deploy-verify | 观测期无异常，指标在基线内 | 观测报告 |

## 阶段衔接规则

- 🔴 **串行推进**：阶段 N 的 Quality Gate 未满足，禁止进入阶段 N+1。
- 🔴 **需求分析先行**：阶段 1 必须先产出需求文档并经用户确认，才可进入阶段 2；禁止跳过需求分析直接写方案。
- 🔴 **确认门**：阶段 1 需求文档与阶段 2 细化方案均需用户确认后才进入下一阶段。
- 🟢 **回退**：任一阶段失败，按回滚路线表回到对应阶段重来。

## 流程路径分级（Modification Level ↔ 阶段 0-10）

| 级别 | 改动类型 | 流程路径 | 强制 Gate（不可省略） |
|---|---|---|---|
| L0 | 文档 / 文案 / 注释 | **轻量**：阶段 1-3 合并为一次（summary 简版），直接阶段 4-5 后阶段 6 快评 | 红线零违反 + 变更追踪 |
| L1 | 面板样式 / 前端展示 | **轻量**：同上，但必须 `node --check` + `go build` | 红线 + 语法检查 + 构建 |
| L2 | 业务逻辑 / 接口 / 调度 | **全流程**：阶段 0 + 十阶段逐项，需求文档 + summary 不可省略 | 阶段 1 需求确认 + 阶段 6 评审 + 测试全绿 |
| L3 | 架构 / 数据模型 / 上游协议 | **全流程 + ADR**：阶段 0 + 十阶段逐项 + ADR 先行 | L2 全部 + ADR + 迁移往返 |

**小改动判据（L0/L1 轻量路径适用，全部满足才可合并阶段 1-3）**：
1. 无行为变更（改样式/文案/纯文档）。
2. 无接口契约、数据模型、上游协议变更。
3. 改动文件 ≤ 3 个且不触承重墙（选号/冷却熔断/凭证链路/出站改写管线）。
4. 不满足任一 → 走全流程路径。

## 阶段 4 编码纪律

- 40% 分批编码、批批验证：一次改动 ≤ 40% 总量 → 编译/测试 → 下一批。
- 变更记录写 `.harness/changes/{feat-name}/summary.md`（与 git 分支同名）。

# 二、分支与提交规范

| 项 | 约定 | Example |
|---|---|---|
| 特性分支 | `feature/{feat-name}`，与 `.harness/changes/{feat-name}` 同名 | `feature/panel-redesign` |
| 修复分支 | `fix/{issue-or-bug-desc}` | `fix/expiry-card-hidden` |
| 主分支 | `main`（自托管，单人项目可直接提交但需变更追踪） | - |
| Commit | `type(scope): message`，type 用 feat/fix/refactor/test/docs/chore | `feat(panel): 到期卡片默认可见` |

- 🟢 Commit subject ≤ 72 字符，body 讲 why；缺陷修复与功能/测试分开提交。
- 🟢 破坏性改动走 expand-contract：先 expand（新旧并存、CI 保持绿）→ 分批迁移 → contract（旧形式无引用后删除）。

# 三、回滚路线表

| 阶段 | Rollback Strategy | Trigger |
|---|---|---|
| 编码实现 | `git checkout` 丢弃变更 | 编译失败 |
| 单元测试 | 修复代码 + 重跑测试 | 测试失败 |
| 二进制部署 | 回退到上一版二进制（保留 `*.orig` 备份） | 冒烟失败 |
| 线上观测 | 回退二进制 + 恢复 `state.json` | 观测期指标越基线 |

- 🟢 **二进制替换前必须备份**：`yg-gateway.exe` → `yg-gateway.exe.v{旧版本}`。本机 `bin/` 下已有多个版本备份。
- 🟢 **凭证目录独立**：`auths/` 不随二进制回滚，删除即不可恢复（需重新 OAuth）。

# 四、代码 review

## 评审维度（6 维）

1. **正确性**：逻辑、边界、状态流转
2. **性能**：并发 / 锁竞争 / 上游请求量 / goroutine 泄漏
3. **安全**：凭证泄露 / XSS / 路径穿越 / 越权 / 日志脱敏
4. **一致性**：与 wiki 接口/数据模型/术语一致
5. **可维护性**：命名、抽象、重复、复杂度
6. **架构合规**：分层、依赖方向、红线

## 问题分级

| 级别 | 含义 | 处理 |
|---|---|---|
| 🔴 阻断 | 红线/安全/数据错误 | 必须修复，禁降级合入 |
| 🟡 主要 | 功能缺陷/性能风险 | 清零后才可过评审 |
| 🟢 次要 | 可维护性建议 | 记录即可 |
| 🔵 提示 | 风格/微优化 | 不阻塞 |

## 评审约束

- 🔴 红线问题禁止降级；🟡 未清零不过评审。
- 🔴 **L2 及以上必须有一次独立复审**（另一会话 / 子代理 / 他人），且复审者**只读**。
  自己写的 `review.md` 只能算「自评审」，**不能作为唯一凭据**。
  实证（2026-10-17）：一份自评审 PASS + 已提交的改动，被独立复审判 **FAIL（3 条 🟡）**——
  自评审漏掉的正是"脚本里 git 调用不判退出码""`core.quotePath` 让中文名文件在 CI 静默跳过"
  这类**只有站在门外看才会怀疑**的问题。复审结论与自评不一致时，以独立复审为准并当场修。
- 🟢 评审记录落盘 `.harness/changes/{feat}/review.md`；多轮评审按轮次分段记录，
  **不许用新一轮结论覆盖上一轮**（要写明"第 1 轮 PASS 已被第 2 轮 FAIL 取代"）。
- 🟢 评审-修复闭环 ≤2 轮；第 2 轮仍不过 → 暂停，人工介入。

# 五、提交前验证矩阵

> 🔴 **提交前必跑总闸**（与"部署前必须备份"同级，不可跳过）：
> ```powershell
> powershell -NoProfile -File scripts/pre-commit.ps1
> ```
> 它把自动化项与红线 R10 一次性变成退出码，任一项失败即退出码 1。
> **完整检查清单以 `scripts/pre-commit.ps1` 自身为准，不在此处逐项复制**——
> 清单一复制就必然漂移（2026-10-20 实测：本段原列 7 项，实际已是 10 项；同类漂移当天还在
> `LESSONS.md` L-1/L-3 里各修了一处）。这是 Handbook 点名的「层次冲突」反模式：
> 同一约束在两处说，模型会随机挑一个（通常是过期的那个）。
> `-Fast` 只跳过 `go test`（赶时间时用，提交前必须至少全量跑一次）；`-Install` 可装成
> `.git/hooks/pre-commit`——此后**每次**提交都会跑全量测试（约 40s+），多会话并行改同一工作区时建议不装。

## 本地与 CI 的分工（本地绿 ≠ 一定过）

| 层 | 在哪 | 覆盖什么 | 为什么需要两层 |
|---|---|---|---|
| 提前发现 | 本地 `scripts/pre-commit.ps1` | **本次改动**的 .go 文件 gofmt · R10 新增行 · `go build`/`go vet`/`go test` · 边界 · 深度棘轮 | 快、可反复跑；代价是 `--no-verify`、忘跑、或并行会话直接 push 都能绕过 |
| **最终闸门** | CI `release.yml` 的 `gate` job（实现见 `.github/workflows/gate.yml`） | **全仓** gofmt · R10（`git diff <base>...HEAD`） · 边界 · **深度棘轮（失败即红）** | 不可绕过；同一条流水线的 `build` 与 `build-image` 都 `needs: gate`，gate 红就不产出任何产物 |
| 功能测试 | CI `test` job | `go test ./...` · `go vet` · `node --check internal/panel/app.js` · `govulncheck` | 与 gate 并行，互不阻塞 |
| 竞态检测 | CI `race` job | `go test -race ./...`（`CGO_ENABLED=1`） | **由 CI 独占**：本机无 gcc，本地跑不了 |

两个容易搞错的点：

1. **棘轮的权威值由 CI 强制**：`check-depth.ps1` 读 `.harness/depth-baseline.json`（入库文件），
   本地 `-Update` 抬棘轮后**必须提交该文件**，否则 CI 仍按旧基线判。**只许收紧**。
2. **CI 里「本次改动」≠ 工作区 diff**：CI 的工作区是干净的，改动早已提交，所以 gate job 传
   `-Base <base>`，R10 与改动文件清单都按这个差分算。不传 / 传错 base 会让 R10 变成
   「检查了 0 个文件」或「只检查了最后一个提交」的假绿。
   **base 怎么解析（单一写点，见 `.github/workflows/gate.yml`）**：PR → `origin/<base_ref>`；
   tag push → 上一个**发版** tag（排除 `-ci` 演练 tag）；branch push → 事件的 `github.event.before`；
   都没有 → `HEAD~1` **并打 `::warning::`**，不静默降级。

| 改动面 | 本地必跑（提交前） |
|---|---|
| 任意改动 | `go build ./...` + `go vet ./...` + `go test ./...` |
| 前端（面板 app.js / index.html） | 上列 + `node --check internal/panel/app.js` + **重新编译二进制**（go:embed） |
| 安全相关 / 依赖变动 | 上列 + `govulncheck` |
| 上游协议 / 出站报文 | 上列 + 真实账号端到端冒烟 |
| 治理/文档 | `scripts/pre-commit.ps1 -Fast`（R10 判据 + 边界 + 深度棘轮）；`.harness/**`、`scripts/**` 的改动由 CI `gate` job 覆盖 |

# 六、完成标准

- [ ] **阶段 0 必要性分析已落纸**（四个问题 + 一个结论；结论「不做/等条件」的已写进规划文件的重评条件）
- [ ] 十阶段 Gate 逐项满足（小改动合并场景：summary + 红线 + 冒烟不可省略）
- [ ] 分支规范符合（feature/fix + conventional commits）
- [ ] review 通过无 🔴、🟡 清零
- [ ] 变更已追踪（`.harness/changes/{feat-name}/`）
- [ ] 回滚路线明确（二进制备份可回退）
- [ ] 观测期通过（无异常）
- [ ] 治理数字改动已同步 AGENTS.md + 对应规则文档（漂移当场修）
