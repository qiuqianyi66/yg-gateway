# LESSONS.md — 踩过的坑与「第 2 次即上规则」阈值

> **机制（Seen 计数制，抄自同源项目 magpie）**：每个坑先记 `Seen` 次数与场景。
> **同一类坑第 2 次出现，就必须升级为规则**——写进 `.harness/rules/`，或（更好）变成
> `scripts/` 里的机器检查。目的：不靠「记得住」，靠计数触发制度化。
>
> **动手前先读本文件**（`AGENTS.md` 的 Development 段已指向这里）。
> 新增条目的写法：先加一条带 `Seen: 1` 的记录；第 2 次遇到时不要只加计数——要在这里写出
> 「升级为什么规则/机器检查」，并回链到落点。
>
> 与 flake 的区别：本文件记的是**会伪造结论**的坑（让人得出错误判断）；
> 已知的时间敏感 flake 记在 §二，属于待修缺陷，不是流程教训。

## 一、坑清单

### L-1｜PowerShell 5.1 的引号 / 反引号陷阱 —— **Seen: 3 → 已升级为规则 + 机器检查**

- **Seen 1**（2026-10-16，上一会话）：`scripts/pre-commit.ps1` 里用「反引号 + 双引号」做转义，
  双引号被吃掉 → 脚本解析失败，门禁整个跑不起来（HANDOFF §4 坑 4）。
- **Seen 2**（2026-10-16，本会话 T3 前）：内联命令里写
  `"...`n`n// 中文注释：…`n`t_ = v..."`（中文串里混反引号与 `` `t ``）→
  ParserError「Missing ')' in method call」，**整条命令一个字符都没执行**。
- **Seen 3**（2026-10-16，本会话 T7-P3/P4 提交时）：`git commit -m "…'stream':\"true\"…"` ——
  提交信息里为转义 ASCII 双引号写了「反斜杠 + 双引号」，PS 双引号串在那里**提前结束**，
  参数被切碎 → git 报 `fatal: '/': '/' is outside repository`，**提交没发生**（工作区已 staged，
  但 HEAD 未动）。危害同 Seen 2：执行者以为提交成功了。
- **根因**：PS 5.1 里反斜杠不是转义符、反引号才是。凡是「在 PS 串里表达双引号」的场合，
  用反斜杠转义都会破坏引号边界。这不是「写清楚点就行」——它是**同一处**反复发生的机制性坑。
- **规则**：
  1. 行内引用一律用「」（中文直角引号），不用反引号、不用反斜杠转义；
  2. 多行内容用单引号 here-string（`@'...'@`），或**写进文件**再由命令读；
  3. **提交信息一律写文件 + `git commit -F <file>`**（Seen 3 之后的最佳实践：提交信息里出现
     引号/反引号/方括号的概率很高，走文件就没有任何转义层）。
- **机器检查（Seen 3 落地）**：`scripts/pre-commit.ps1` 检查 3/6 —— 新增的 `*.ps1` 行里出现
  「反斜杠 + 双引号」即失败（该形态在 PS 里**一律是 bug**，误报率为零，因此与 Seen 2 时
  「无法机器化」的判断相反）。**边界**：命令行里的一次性用法不在版本库里、无法被这条检查覆盖，
  只能靠规则 1–3 与「提交走 `-F`」的习惯兜住。

### L-2｜变异测试必须在**副本**里做，且断言「我在副本里」—— **Seen: 2 → 已升级为硬规则**

- **Seen 1**（2026-10-16，上一会话）：有 agent 的变异脚本 cwd 落在**原件**，
  `go test` 实际测的是未变异的源码 → 输出「5/5 全存活」的**假结果**
  （agent 自己发现并作废，未污染结论）。
- **Seen 2**（2026-10-17，B1a 的变异验证）：为证明新测试有牙齿，我**直接改了真实工作区的
  `internal/server/chatrun.go`**（备份/还原 + 前后 SHA256 比对，当时比对「一致」）。但同一时刻
  **另一个会话也在改同一棵工作树**；事后独立复审发现该文件停在**变异态**
  （`B3CB56DA…` vs HEAD `44BADD08…`）——若被原样提交，等于**静默回退一个生产修复**。
  我还一度把这份脏状态误判成「并行会话的在途改动」。
- **根因（两次相同）**：**变异写在真实工作区里**。Seen 1 是 cwd 落在原件（测的不是变异），
  Seen 2 是变异落在原件（留下脏状态 + 误判归属）。方向相反，同一根因。
- **规则（不再是建议）**：
  1. 变异**一律**在 `%TEMP%` 副本里做，并在副本里先断言 `go env GOMOD` 指向副本的 `go.mod`；
  2. 确需原地做（例如依赖真实 git 历史）→ 先 `git status --porcelain` 存档，做完
     `git checkout -- <file>` 还原，并**再次** `git status` 断言该文件不再出现；
  3. 报告里引用「哈希闭环」时要写明是**副本**还是**原地**——两者可信度不同；
  4. **多会话共用一棵工作树时，任何「临时改动生产文件」都是在给别人埋雷**
     （本次的雷：一份真实的修复被静默回退）。
- **为什么没有机器检查**：无法自动判断「这次改动是变异还是真改」。可自动化的只有事后守卫
  （比对已提交文件哈希与某份基准），而基准需要人维护，收益不抵复杂度 → 升级为**硬规则 +
  报告口径要求**，而不是机器检查。

### L-3｜单引号/未加引号的变量 → 生成字面名垃圾文件 —— **Seen: 2 → 已升级为规则 + 机器检查**

- **Seen 1**（2026-10-16）：`-coverprofile=$out`（单引号）在仓库根生成了 `$out`/`$p`/`$tmp`
  三个文件，内容是覆盖率 profile（已清理）。
- **Seen 2**（2026-10-16，T5）：`-coverprofile=$cov`、`-coverprofile=$abs`（**未加引号**，
  看起来像是正常插值）在仓库根生成 `$cov`（52928 字节）/`$abs`（2492 字节）两个 profile 文件。
  探针实测（`cmd /c echo -coverprofile=$x`）：
  ```
  未加引号: -coverprofile=$x      ← PS 5.1 根本没展开，原样进了原生命令
  加了引号: -coverprofile=VAL
  ```
  即坑比 Seen 1 记的**更宽**：不只是单引号，未加引号的 `-flag=$var` 同样不展开，
  而且它不报错、只是把 profile 写到名为 `$cov` 的文件里——静默，且看起来像成功。
- **规则**（升级）：给原生命令传「带变量的参数」一律写 `"-flag=$var"`（**双引号**）；
  覆盖率/临时产物一律 `"-coverprofile=$env:TEMP\xxx.out"`（绝对路径）。
- **状态**：**已机器化（2026-10-16，N2）**。落点 `scripts/pre-commit.ps1` 检查 4/7
  「仓库根的字面名垃圾文件」：扫**未跟踪 + 仓库根**的文件，名字以 `$` 开头、
  或形如 `out`/`p`/`tmp`/`cov`/`cover`/`profile`（可带前导点）即失败，并在输出里直接给出正确写法。
  **改扫「产物」而不是扫「diff 里的写法」**：原候选是扫新增行里的 `-\w+=\$` 形态，但那种写法
  必然要处理引号/换行/跨行等边界、误报面大；而这条坑的产物是**一个具体的文件**，
  `$` 开头的文件名在仓库根不可能有正当用途 → 该分支**零误报**。字面名分支（`out`/`p`/`tmp`/
  `cov`/`cover`/`profile`）是刻意收窄的枚举，**不是**零误报：仓库根一个合法但未跟踪的 `out`
  会被拦下，出口是把它加进 `.gitignore` 或改名（提示里写了）。漏判方向：名字不在枚举里
  （`cov.out`、`badfile`）不拦——真实坑的产物都是 `$xxx`，由 `StartsWith('$')` 分支覆盖。
  三条负向探针 + 一条误报探针见 `.harness/changes/2026-10-16-precommit-l3-check/summary.md`。

### L-6｜CI 里「本次改动」≠ 工作区 diff —— Seen: 1 → **已机器化**

### L-7｜反斜杠字面量路径在 Linux 上不是分隔符 —— Seen: 1（**候选规则，未达 2 次**）

### L-9｜换二进制要等端口释放，且别信 `start.bat` 的重定向 —— Seen: 1（**会短暂打断生产**）

- **Seen 1**（2026-10-16，T7 部署）：按「停 → 换 → 启」的纪律做，但 `stop.bat` 之后只等 2 秒就启动新版本 →
  新实例没起来（端口仍被旧监听占着），健康轮询 30 秒超时 → 脚本自动回滚到备份。
  **代价**：生产中断约 **1 分钟**（本会话自身的模型调用也走这个网关，同样被中断）。
- **根因**：Windows 上 `taskkill /F` 返回后监听套接字不会立刻释放；2 秒是拍的，不是测的。
- **附带发现**：`start.bat` 里的 `start ... >> data\stdout.log` **不会**把子进程输出落到那个文件
  （重定向加在 `start` 自己身上）→ 新实例起不来时**没有任何日志可查**，只能靠猜。
  另：`start.bat` 里的 `timeout /t 3` 在 stdin 被重定向时会打
  `ERROR: Input redirection is not supported`（噪音，不代表启动失败）。
- **规则**：
  1. 换版前**轮询端口释放**（`netstat -ano | findstr ...LISTENING` 为空）再启动，别拍固定秒数；
  2. 启动要**捕获新实例自己的 stderr**（`Start-Process -RedirectStandardError <file>`），
     且回滚那次用**另一个**日志文件，否则回滚会覆盖失败现场；
  3. 健康轮询 + 失败自动回滚（恢复到备份 exe 并重新拉起），把「中断」限制在一次尝试之内。
- **状态**：本次已按 1–3 执行成功（第二次尝试：端口释放 → 启动 → 健康 → 冒烟全过）。
  候选：把这套流程固化成 `scripts/` 下的换版脚本（含备份/端口轮询/日志/回滚），避免下次靠记忆。



### L-10｜改文件要用定点编辑，别做「字符串手术」 —— Seen: 4（**会静默丢内容**）

- **Seen 1**（2026-10-16，T7 补记）：用「替换整段」的方式给 `.harness/changes/2026-10-16-t7-unknown-admission/summary.md`
  追加 §六，锚点选成了 §四 的整段 → **§四（怎么回滚）被覆盖**，章节编号变成一、二、三、六、七、五。
  最终整篇重写才修好。
- **Seen 2**（2026-10-16，T7 部署后）：同样的手法给本文件追加 L-9，锚点写成 `## 二、已知 flake` 标题行 →
  标题被吃掉、**§二 的标题连同所属关系丢了**（表格变成无主内容）。靠 `git show HEAD:<path>` 精确还原才救回。
- **Seen 3**（2026-10-16，紧接着）：还原时用 .NET `WriteAllText` 自己拼行、用了 CRLF，而仓库是 LF →
  `git diff` 显示**整篇 144 行重写**（118 删 144 增），把「只加了一条教训」伪装成「全文重写」；
  另因第一次追加失败留下残块，还原后表还重复了一遍。
- **Seen 4**（2026-10-16，N1 生产实弹的调度）：用**字符串拼接**生成一个行敏感的 `.cmd` 包装脚本
  （`'... -ReportPath "' + $tmp + '\n1-livefire-report.json" ...'`）。命令被运输层按行拆开后，
  落到 `.cmd` 里变成 `-ReportPath "` →换行→ `C:\...\Temp` →换行→ `\n1-...`：
  cmd 把下一行当成新命令、`>` 重定向目标断成两截。**后果**：换版本身成功了，但脚本的报告与
  控制台日志都没落盘——实弹那一轮只剩「生产确实换了版」一项证据，冒烟结果无从查证。
  与 Seen 1–3 同一根因（**用拼接/拼行去构造文件内容**），只是这次受害的是 `.cmd` 而不是 `.md`。
  修法：行敏感的文件（`.cmd`/`.bat`/`.ps1`/脚本夹具）一律用**编辑工具写字面内容**，
  路径一律走变量/`Join-Path`，不要在一行里把「字面片段 + 变量 + 字面片段」拼起来交给外层再解释一遍。
- **根因**：把「追加一段」实现成「用一段文本替换另一段文本」，锚点一旦选错就**吃掉内容**；
  自己拼行又引入与仓库不一致的行尾。两类都属于**看不见的破坏**：文件还在，内容没了。
- **规则**：
  1. 追加内容时，锚点选**你要保留的那一行**（如 '# 二级标题'），把新内容放在它**前面**；
     不要拿「整段旧内容」当锚点；
  2. 改完**立刻核对**：结构（`Select-String '^## |^### '` 看章节齐不齐、有没有重复）与
     diff 规模（`git diff --stat`：只加几行就该只有几行）；
  3. 恢复被覆盖的内容要**从已提交版本取**（`git show HEAD:<path>`），不凭记忆重写；
  4. 手写文件一律 LF（与仓库一致），或用编辑工具写，别自己拼行。
- **状态**：三条都在提交前被自己发现并修回，没有进入历史。候选：把「追加型改动先看 `git diff --stat`」
  写进提交前自检清单（`.harness/rules/CODE-STANDARDS-CHECKLIST.md` §十）。

### L-11｜测试必须和它依赖的生产改动同一个提交 —— Seen: 1（**会让 HEAD 本身跑不过**）

- **Seen 1**（2026-10-16，CI 首跑）：`internal/panel/coverage_handlers_test.go:1182` 断言面板响应里
  有 `cost_ppm == 500` / `cost_samples == 1`，而产出这两个字段的 `internal/panel/panel.go` 改动**尚未提交**
  （并行会话的工作区改动，+23 行）→ **本地 `go test ./...` 全绿，CI 红**。
  同一根因还顺带暴露了另一件事：`panel.go` 在 **HEAD 上有 gofmt 漂移**，而本地因为工作区版本已被
  改过/格式化过所以看不出来。
- **危害**：这不是「测试写错了」，而是**提交的可复现性被破坏**——任何人 clone 到 HEAD 都会红；
  而当事人本地永远绿，于是很容易误判成「CI 环境有问题」。
  它同时说明「本地绿」作为证据的边界：**本地工作区可能含未提交改动**，CI 跑的是 HEAD。
- **规则**：
  1. 提交前用**干净 HEAD 的独立工作树**再跑一次（最快自查）：
     `git worktree add "$env:TEMP\ci-check" HEAD --detach` → 进去 `go test ./... -count=1` → `git worktree remove`
     （本次就是这么定位的：在 HEAD 工作树里 `TestPanelHandlersModels` 立刻复现）；
  2. 测试与它依赖的生产改动**同一个提交**；做不到就先别提交那个测试；
  3. 看到「本地绿、CI 红」的第一反应是查「HEAD 与工作区的差集」，不是怀疑 CI。
- **状态**：本次已定位并记录；修复需并行会话把 panel WIP 提交（本会话未越界代提交）。

### L-12｜把非 PE 当 exe 启动会弹模态对话框，把 launcher 卡死 —— Seen: 1（**会伪造结论 + 短暂停服**）

- **Seen 1**（2026-10-16，N1 排练）：为验证「坏 exe → 自动回滚」，把一个 **33 字节的文本文件**
  当网关 exe 启动。Windows 兼容层弹出**模态对话框**「不支持的 16 位应用程序」，
  而 launcher（`cmd.exe`）就阻塞在「等人点确定」上。**用户在桌面上看到了这个弹窗**。
- **连锁现象**（三条都是同一个根因，看起来像三个不同的 bug）：
  1. 新实例的 **err 日志 0 字节** —— 错误进了对话框，没进被重定向的 stderr → 失败时无日志可查；
  2. 那个 exe 文件被**持续占住**（实测 15s 以上不释放）→ 覆盖式回滚写入失败（见 L-14）；
  3. launcher 进程**永久残留**，桌面上留一个需要人工点的窗口（点完才继续）。
- **另一条独立的坑（同一次实验里量到）**：`Start-Process -RedirectStandardOutput/-RedirectStandardError`
  起的**常驻**孙子进程，会持有调用方 stdout 管道的写端 → 用 `& powershell -File xxx.ps1`
  捕获输出时，外层**一直阻塞到该进程退出**。实测：内层脚本 3s 结束，外层阻塞 **8865ms**
  （≈ 孙子进程的 8s 睡眠）；换成 cmd 重定向后外层 **3716ms** 正常返回。
  危害：CI / agent harness / 任何「捕获输出」的调用方会白等一个常驻服务的寿命。
- **规则**：
  1. 启动服务前对候选二进制做 **PE 预检**（MZ + `PE\0\0` 签名），把「根本不是可执行文件」
     挡在**停服与启动之前**——非 PE 读文件头就能判定，没有理由先启动它；
  2. 要同时做到「日志落文件」＋「不拖住调用方」，用
     `cmd /c "<exe>" -config "<cfg>" > "out" 2> "err"`，且**整串再包一层引号**
     （不包的话 cmd 会剥掉最外一层引号、连同重定向一起吃掉 →
     **进程静默不启动**：实测 listeners=0、日志 0 字节、**没有任何报错**；包了之后
     listeners=1、stderr 1047 字节）；
  3. **别**用 `Start-Process -RedirectStandardOutput/-RedirectStandardError` 起常驻服务。
- **落点**：`scripts/deploy-prod.ps1`（`Test-PeImage` / `Start-Instance`）与
  `scripts/deploy-prod.rehearsal.ps1`（A1 钉预检、B 钉「不拖死调用方」的 30s 上界）。

### L-13｜PS 5.1 的 `Invoke-WebRequest` 非 2xx 时 body 已经被读掉 —— Seen: 1（**会伪造结论**）

- **Seen 1**（2026-10-16，N1 排练）：换版脚本的健康检查对 **503** 响应读
  `$_.Exception.Response.GetResponseStream()` → 读到**空串** → 「服务活着但 0 账号」被判成
  「没有任何响应」→ 误触发回滚。代价：排练一次刷出 **14 项假失败**，
  且**回滚把本来成功的部署退回了旧版**——看起来像「部署功能坏了」，实际是检查器坏了。
- **根因**：`Invoke-WebRequest` 在非 2xx 时自己已经把 body 读进 `ErrorDetails`（这也是
  `catch { "$_" }` 能直接打出响应体的原因），响应流到我们手上时已到 EOF。
- **规则**：
  1. 凡是要**判服务的结构化状态**（健康、就绪、错误体）的场合，不要用 `Invoke-WebRequest`，
     直连 `System.Net.HttpWebRequest`：状态码与 body 都自己读，非 2xx 也有体；
  2. 判「健康」不要只认 2xx —— `/healthz` 在 **0 账号时返回 503**（探针实测），
     只认 200 会把「起来了但没账号」误判成「没起来」。
- **落点**：`scripts/deploy-prod.ps1` 的 `Get-HttpResult` / `Test-HealthOnce`。

### L-14｜覆盖一个被占用的 exe 会失败，必须改名替换 —— Seen: 1（**会让回滚写不回去**）

- **Seen 1**（2026-10-16，N1 排练）：坏 exe 的 launcher 占着 `yg-gateway.exe`，
  回滚时 `Copy-Item 备份 → yg-gateway.exe -Force` **持续失败**
  （`file is being used by another process`，重试 10s 仍失败）——
  **恰好发生在最需要回滚的时候**，而这正是换版脚本唯一存在的理由。
- **实测三种写法**（同一锁状态下）：

  | 写法 | 结果 |
  |---|---|
  | `Copy-Item 好exe → 原名字 -Force` | **失败** |
  | `Copy-Item 好exe → 原名字.staged` + `Move-Item -Force` 改名替换 | **成功** |
  | 杀掉占用者再直接覆盖 | （未测完；不必需，因为上一行已解决） |

  差别在于：**覆盖要拿目标文件的写权限，改名只需要 `FILE_SHARE_DELETE`**。
- **规则**：替换/恢复二进制一律「写 `*.staged` + `Move-Item -Force` 改名替换」，
  不要直接覆盖目标名。同类场景：任何「正在被进程持有的工件」的原子替换。
- **落点**：`scripts/deploy-prod.ps1` 的 `Replace-Binary`（正向替换与回滚**共用**它）。

### L-15｜否定性断言必须穷尽证据源 —— **Seen: 2 → 已升级为事实纪律条款**

- **Seen 1**（2026-10-17，交接文档 `HANDOFF-2026-10-16-ci-closed.md` §3 N6）：
  它把「wiki 挑出的重构建议」转述成 4 个具体短语（退避与额度解耦 / 快过期积分纯函数 /
  流式 error 门禁 / 写回前回读），并指向 `.harness/wiki/cc-switch-deep-read.md`。
  实际**全仓 grep 四条短语 0 命中**，wiki 自己的「该改」是另外四件事
  （剪枝前回填 / 持久化版本闸门 / 跨文件写前意图 / 清理时机）。
  后果：接手者会照着不存在的条目开工，或以为 wiki 已被完整吸收。
- **Seen 2**（同日，我自己写进规划并推送）：`docs/PLAN-open-items-2026-10-17.md` 的 B6 写
  「`check-depth.ps1` 只报计数不报明细、`$longFuncs` 内部有完整列表但**从不输出**」——
  实际脚本有 `-Detail` 开关，早就打印 5 个超长文件 + 7 个超长函数（7/7 全列）。
  我只读了「定义处」与「计数 `Write-Host` 处」两个引用点就下了全称否定。
- **根因**：正向断言一个样本就够，**否定断言要求穷尽**。而否定断言一旦写进规划/交接/变更记录，
  它的危害不是「查错了一处代码」，是**误导下一轮的工作分配**（比功能缺失更危险：它不报错）。
- **规则（写在 `AGENTS.md` 的「事实语义纪律」，那里是四态的最高权威）**：
  1. 给**全仓 grep 的原始输出**，或列出**全部**引用点逐个看过；「定义 + 一处引用」不算；
  2. 不把转述（交接文档/摘要/二手规划）当原始出处——要引就引被引用的那份文件本身；
  3. **机器能跑的优先实跑**（`-Detail`、`--help`、`-List`）：跑一次比读三处快，而且不会漏；
  4. 做不到穷尽就写四态里的 **unknown**（「未覆盖 = 未知」），不许写成否定。
- **为什么不是机器检查**：这条断言的对象是**自然语言文档**（`_ =` 那种形态反而可机器化）。
  能机器化的是「文档里出现的选项名/函数名在代码里是否存在」，但那会把 `-List` 这类**尚未实现**
  的开关也判红，误报率高。故升级为**规则 + 复核习惯**，落点 `AGENTS.md`。

### L-17｜「变异全绿」先问一句：跑的是副本吗 —— **Seen: 1 → 已升级为机器检查**

- **Seen 1**（2026-10-18，A-1 夜猫子 B4a 验证）：在 `%TEMP%\mut-nightchat` 副本里把
  `if i < need-1` 改成 `if true`（旧行为），`go test` 却**全绿**，差点判成「测试没咬住」。
  真因：**工作目录是会话根目录**——`go test ./internal/upstream/` 读的是原树 + 构建缓存，
  副本里的改动根本没被编译。
- **为什么危险**：「变异全绿」在核验里意味着「测试有缺口」，而真实含义是「我没测到我以为在测的代码」。
  绿比红更容易被接受，所以这个坑不会自己暴露。
- **规则（ad-hoc 验证必须自证）**：
  1. 显式把 `workdir` 指到副本（用工具参数，不要靠 `cd`，它只影响那一条命令）；
  2. `go test -count=1` 禁缓存，或 `go env GOMOD` 断言指向副本；
  3. 输出里出现 `(cached)` 一律读作**未生效**，不是「通过」。
- **机器检查**：`scripts/mutation/mutation-check.ps1` 原本就有 GOMOD 断言 + `-count=1`；本轮再补一条
  **`(cached)` ⇒ 判「无效变异」**，把这条从「靠人记得」变成「脚本拒绝」。手写临时验证没有 driver
  兜底，规则 1/2/3 要自己照抄。

### L-18｜外部工具验证：就绪判据必须是真实状态，不是「等一会儿」 —— **Seen: 1**

- **Seen 1**（2026-10-19，B1b 面板像素观感）：连着两次截到空壳（页面全是「—」）。

- **为什么不是纯机器检查**：「等什么算就绪」依赖场景；但**轮询 DOM** 这一步已固化进脚本默认行为。
